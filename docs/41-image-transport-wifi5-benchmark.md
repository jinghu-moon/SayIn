# 41 · 图片传输 Wi-Fi 5 真机基准

日期：2026-11-14。状态：**真实手机到电脑的局域网网络实验已完成；图片业务与生产协议未实现或替换。**

后续已完成 [42 双 WSS 与双 TLS 同期六轮补测](42-double-wss-wifi5-benchmark.md)。下文仍保留第一次五配置实验的原始结论和数据，不混用两批测量；本次初始工具的精确 [Rust 源码](benchmarks/2026-11-14-wifi5/main.rs)和[锁文件](benchmarks/2026-11-14-wifi5/Cargo.lock)另行归档。

## 1. 结论

当前这套 Wi-Fi 5 网络可以传送本次全部图片。三轮、五种配置、八张图片，共 **120 次、1,511,516,265 字节有效图片数据**，全部收到摘要校验成功确认，无连接错误或上传超时。

- 约 2 MiB 的图片传输中位数为 0.198～0.218 秒，10 MiB 约 1.02～1.07 秒，25 MiB 约 2.56～2.74 秒，56 MiB 约 5.95～6.25 秒。这是已连接状态的网络与摘要确认耗时，不是选择图片到目标软件显示的耗时。
- 五种配置的大图吞吐接近。当前样本不能支持“换成 QUIC 就显著更快”或“图片分四路就能四倍加速”。
- 最显著的差异是控制延迟。大图传输时，**单 WSS 控制 echo RTT p95 为 1565.6ms，控制/图片分离 TLS 为 76.8ms**。在应用层优先发送控制消息，仍不足以解决共享 TCP 连接中已排队图片字节的阻塞。
- QUIC 1/2/4 图片流的对应 p95 为 115.4/495.6/215.3ms，未胜过本次分离 TLS 原型；2/4 流没有稳定吞吐收益，部分回合尾延迟反而较大。不能把这个实现、参数和网络下的结果推广成 QUIC 协议的普遍上限。

**下一步建议：先采用“一条控制通道 + 一条有界图片通道”的架构验证，不默认增加单图并行。** 本次没有独立对照“两条 WSS”和“两条 raw TLS”，因此证明的是传输隔离的实际价值，不能证明 WSS 帧格式本身比 raw TLS 慢，也不能单凭这次实验定下控制协议的最终帧格式。QUIC 保留为后续弱网、切网及实现成本对照候选，不为维护旧协议而保留旧结构，也不为追新协议而替换。

## 2. 基线与隔离

- 共同代码基线：`f9b52bec3513515d14be3ebd75fac1946120e7b3`。
- 实验在独立 worktree、分支 `codex/image-network-bench` 开发；未改动其他 worktree。
- 增加独立的 [Rust CLI](../scripts/image-transport-bench/README.md)，同一份源码编译 Windows MSVC 和 Android aarch64。没有安装 APK，没有改动应用包名、生产配对、证书、令牌、草稿、Outbox、历史、输入执行器或日常 SayIn 进程。
- 每次服务生成临时自签名证书、私钥和随机 32 字节 token。客户端只信任本次证书，验证 TLS 名称和完整 DER 后才发送 token；服务私钥只在电脑内存中。
- 电脑只绑定 `192.168.71.6`，测试 TCP `54754`、UDP `60112`；手机显式绑定 Wi-Fi IPv4 `192.168.71.72`。未绑定全部接口，未走 FlClash 的虚拟接口。
- ADB 只用于分发工具/图片和拉取记录；未创建 ADB reverse/forward。设备已有、与本次无关的 `tcp:17888` reverse 原样保留，测试不访问该端口。
- 没有更改防火墙或 Windows 网络类别。**测试时 Windows 三类防火墙配置均已处于关闭状态**，因此本次成功不能用来证明开启防火墙后的 UDP/TCP 授权、产品网络范围约束或自动发现可用。

## 4. 样本与方法

使用 `refer/image-test` 内八张原始 JPEG。目录内实际是文件；文件名的大小只作标签，计量采用实际字节数。原图没有压缩、重编码、解码或改写；没有上传互联网。

| 文件 | 实际字节 | 约合 MiB |
| --- | ---: | ---: |
| `001_370.73KB_1.jpg` | 379624 | 0.36 |
| `002_509.31KB_2.jpg` | 521534 | 0.50 |
| `003_823.82KB_3.jpg` | 843588 | 0.80 |
| `004_1.21MB_4.jpg` | 1268552 | 1.21 |
| `005_2.04MB_5.jpg` | 2136152 | 2.04 |
| `006_10.08MB_6.jpg` | 10567181 | 10.08 |
| `007_25.17MB_7.jpg` | 26392479 | 25.17 |
| `008_55.94MB_8.jpg` | 58658641 | 55.94 |

五种配置：

| 配置 | 连接与流 |
| --- | --- |
| WSS | 一条 TLS/WSS；控制与二进制图片共享，控制队列优先 |
| TLS split | 两条独立 TLS 连接，分别承载控制和图片 |
| QUIC 1 | 一条 QUIC 连接，控制流 + 一条图片流 |
| QUIC 2 | 一条 QUIC 连接，控制流 + 两条图片流 |
| QUIC 4 | 一条 QUIC 连接，控制流 + 四条图片流 |

所有配置图片应用块为 48KiB；每条图片流的应用发送队列最多两块，控制队列最多 32 项。发送方有界读取手机文件；接收方按可信样本清单检查长度和分区摘要后丢弃内容，全部分区校验通过才确认。分区为完整覆盖原图的不重叠连续区间，1/2/4 分区摘要在电脑准备阶段分别计算，不把整张大图读入一个内存缓冲。

QUIC 控制发送流优先级 10，图片为 0；每流接收窗口 2MiB、连接接收/发送窗口 8MiB。TCP_NODELAY 开启，TCP 内核缓冲和拥塞控制使用系统默认。**应用队列有界不等于内核/QUIC 缓冲完全相同**；并行模式的应用队列总预算随流数增加，这些参数是本次实验条件。

三轮依次轮换配置顺序：

1. WSS → TLS split → QUIC 1 → QUIC 2 → QUIC 4。
2. TLS split → QUIC 1 → QUIC 2 → QUIC 4 → WSS。
3. QUIC 1 → QUIC 2 → QUIC 4 → WSS → TLS split。

第 1/3 轮图片从小到大，第 2 轮从大到小。每种配置前后分别采集 1.5/1 秒空闲控制 echo；传图中约每 20ms 发一次控制 echo，计时来自同一手机的单调时钟。RTT 包含程序排队与调度，不是单向网络延迟；采样调度延误时跳过遗漏 tick，不补发一批假定时样本。

上传耗时从发出开始请求到收到全部摘要校验完成确认，包括请求/准备确认、文件读取、加密传输、接收摘要及最终确认。连接/流创建与临时 token 认证不计入每张图片耗时，另记录会话准备时间。未加入人工丢包、断网或限速。

### 5.2 传图时的控制延迟

以下仅聚合三张 ≥10MiB 大图传输时发送的 echo，避免小图过少的样本干扰；单位毫秒，使用 nearest-rank 百分位。每种配置是三轮合计约 1450～1550 个负载样本，不是数千次独立网络环境实验。

| 配置 | 空闲 p50 | 空闲 p95 | 大图样本数 | 大图 p50 | 大图 p95 | 大图 p99 | 大图最大 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| WSS | 2.6 | 12.9 | 1447 | 1054.4 | 1565.6 | 1762.4 | 1905.6 |
| TLS split | 2.4 | 6.7 | 1492 | 23.1 | 76.8 | 158.5 | 215.1 |
| QUIC 1 | 2.5 | 9.8 | 1508 | 37.0 | 115.4 | 185.7 | 278.6 |
| QUIC 2 | 2.6 | 13.1 | 1546 | 44.3 | 495.6 | 802.5 | 958.6 |
| QUIC 4 | 2.5 | 25.0 | 1454 | 57.5 | 215.3 | 897.0 | 1176.6 |

单 WSS 已有二进制分块、有限应用队列和控制优先，并未故意给图片套用文字的 10msg/s 限流。仍出现秒级控制排队，说明“分成小块且下一块前优先控制”不足以约束已进入共享 TCP 发送路径的数据。这是当前实现和默认缓冲条件下的实测，不意味着所有 WSS 实现必然固定延迟一秒。

分离 TLS 显著改善，但满速传图的 p99 仍约 158ms；不能承诺任何网络下的控制实时性。下一阶段若需要更严格的延迟目标，应测试保留带宽、发送节奏和缓冲预算，而不是只增加图片并发。QUIC 不同回合也有丢失检测和明显尾延迟，本次未做抓包/系统调度剖析，不将尾延迟强行归因于某一个协议机制。

### 5.3 其他观察

- 会话准备中位数：WSS 26.6ms，TLS split 23.3ms，QUIC 1/2/4 为 18.6/26.1/26.2ms。该指标含建立连接/流和逐通道认证，通道数不同，**不是纯 TLS/QUIC 握手速度对比**。
- 手机进程累计 VmHWM 最高 21756KiB（约 21.25MiB）。该峰值跨配置累计，不能当作各配置独立峰值；也没有包含图片解码/显示或应用模型内存。Windows 接收测试进程观察到峰值工作集约 14.84MiB，原始字节在环境记录中。
- QUIC 的每轮丢失/发送包计数保留在原始记录，不等同于 Wi-Fi MAC 层丢包率。本次没有向网络人工注入丢包。

## 6. 对图片功能设计的影响

1. **Wi-Fi 5 不构成首版必须升级硬件的理由。** 本次普通大小图片已是几十到几百毫秒传输；大图应显示进度和可取消操作，56MiB 原图不能宣传为瞬间抵达。换路由器是否改善仍需在目标设备和环境复测。
2. **分块用于有界内存、进度和取消，不等于必须多路并行。** 目前一条图片流已达到与四流接近的吞吐，先不加入条带调度、乱序写入和多分区恢复等产品复杂度。
3. **控制与大载荷隔离应成为设计约束。** 是否使用两条 TLS/WSS 连接、或经过调优的一条 QUIC 多流，要同时满足真实环境下的控制延迟、身份绑定、取消/范围变化、网络授权和实现成本；不能仅看图片平均吞吐。
4. **不能据本次网络实验直接扩大生产配额。** 草案 10MiB 上限不是网络硬限制，56MiB 网络传输已通过；但编码大小不能代表解码像素、受保护落盘、历史配额与剪贴板内存。产品最终上限需补齐这些测量再决定。
5. **原来的信任和输入语义仍必须重建在所选承载之上。** 临时实验 token 不是产品配对实现；换协议不能换证书、放弃 host/device/session 认证、绕过暂停/待核对或重连自动重放。
