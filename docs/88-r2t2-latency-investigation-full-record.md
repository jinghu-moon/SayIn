# SayIn Android · Confucius4-R2T2 延迟问题完整过程记录

记录截至 2026-11-25。本文是 [87 性能交接](87-r2t2-performance-handoff.md) 的展开版：87 回答「现在卡在哪里」，本文回答「怎么一步步走到这里」，包括定位、根因、方案、取舍、数据与思考方式。逐轮原始数据以 [84 Android VAD 方案](84-android-vad-design.md) 为准，本文引用而不重复全部表格。

## 1. 目标与验收口径

### 1.1 用户要的体验

1. **点击说话后尽快可说。** 通过预加载、预热和模型实例复用缩短等待；冷启动时保留已采集的首音频，用户一开口不能丢字。
2. **边说边识别，持续增量上屏。** 目标对照是 X-ASR 480 ms 的流式体验。已确认前缀必须稳定，未确认尾部可由最终结果校正，避免重复、闪烁和整段回改。长时间连续说话也要持续更新。
3. **说完后快速定稿。** 点按录音在最后有效语音后自动停麦（静音阈值 2 / 2.5 / 3 秒，默认 2.5 秒），长按松手结束，连续听写由用户结束；手动停麦要快速排空已采集音频。
4. **快速与准确同时验收。** 保留弱起声、短词、真实尾词、中英混说和数字，裁掉确认无效的尾部静音或噪声。原始 ASR 与经过 ITN、CT 后的最终结果分别度量。自动发送只能由成功定稿和现有发送策略触发。
5. **开发期允许重构核心路径。** 先固定基线，用同一输入和同一设备验证改动、相关已有功能和边界，完成后构建 Debug 并覆盖安装到指定手机。

### 1.2 计时口径

所有数字都必须说明起止点，否则无法比较。本文统一使用以下口径：

| 指标 | 起点 | 终点 | 说明 |
| --- | --- | --- | --- |
| 点按到开麦 | 点击录音 | 麦克风开始读 PCM | 与模型预热、冷启动首音频保留相关 |
| 首字 | 回放（供帧）开始 | 第一次非空识别回调 | 不含模型加载与预热 |
| 录音中最长无更新 | 录音开始 | 供帧结束 | 含开头首字前和结尾前的空窗，按识别回调计 |
| 停录到定稿 | 供帧结束（EOF）或手动停麦 | 拿到最终结果 | 静音等待和推理耗时分开记录 |
| 16 秒编码 | 卷积前端起 | Transformer 与投影止 | 分项指标，目标低于 5 秒；不等于整体体验 |

特别说明：

- 本文所有 K40 / K90 / Windows 数据来自**预录 PCM 按实时节奏（每 100 ms 或 80 ms 一块）供帧的回放**，不是真人麦克风。真人麦克风、Compose 实际绘制延迟、长时功耗和目标延迟分位数均未测。
- 「定稿」时延对静音收尾阈值敏感：连续听写与 V3 回放在原录音后补 5 秒静音，手动结束的夹具（如 S-E10、Q-E08 手动结束）不含尾部静音。比较不同行之前必须核对结束方式。
- 热状态和 CPU 频率未固定，同一输入跨批次波动可观（例如标准包同一 Q-E08 同段定稿曾测得 5.47–11.89 秒）。单次差值不能直接归因于某项改动。

## 2. 问题如何一步步暴露

### 2.1 最初的用户感受

用户最先遇到的是**录音时看不到文字，点击结束后还要等很久**。这是两个不同的问题：

- 录音中不出字 → 预览（preview）链路没跑起来或太慢；
- 结束后等很久 → 定稿（final）要重算的内容太多。

### 2.2 第一轮改动与新症状

接入 VAD 自然分段与流式预览后，R2T2 能在录音中发布稳定文字，但出现了新的、更隐蔽的体验问题：**计算跟不上音频采集时，先长时间空白，再一次性连续回调一批 token**。用户的反馈从「不出字」变成「现在速度快了不少，但仍隔几秒分批出字，不及 X-ASR 480 ms，说完还要等」。

接着用户追问三个精确的问题，决定了后续调查方向：

1. 16 秒音频的编码为什么还超过 5 秒？
2. 音频编码和前填各自占多少？
3. K40、K90 Pro Max、电脑三种环境各自表现如何？官方 R2T2 与 `audio.cpp` PR #696 是怎么做的？

### 2.3 早期基线（K40）

| 输入 | 方案 | 首字 | EOF 至定稿 | 备注 |
| --- | --- | ---: | ---: | --- |
| 20.106 秒重复混说 | 固定 16 秒窗口 | 4.501 秒 | 34.188 秒 | 有录音中预览 |
| 20.106 秒重复混说 | 优先消费 VAD 自然边界 | 4.652 秒 | 23.382 秒 | 有录音中预览，但两段接缝出现「星期三昨天」连写 |

结论：VAD 分段确实减少了停录时等待的大段投影与解码（34.188 → 23.382 秒），但 23 秒仍是明显等待，且分段带来了接缝质量问题。这条回放当时**不能作为 R2T2 流畅度放行证据**。

### 2.4 其后的长句现象（贯穿后续全部调查）

- 长句经常出现接近 10 秒甚至更长的**录音中无更新间隔**；
- 短句也可能录音期间不出字，停录后才首次出字；
- 长句定稿还会因积压的推理轮次拖到十几秒。

这三个现象是后续所有方案要验证的对象。

## 3. 根因定位

### 3.1 先确认架构事实

- R2T2 基于 Qwen3-ASR-1.7B，用稳定前缀训练来决定哪些词可以提交。它的音频编码器在一个注意力窗口内双向计算，活动窗口增长时，新音频会改变已有位置的编码表示。
- X-ASR 480 ms 是带流式状态的 Zipformer Transducer，保存编码与解码状态并随新块向前推进。
- 两者解决的是不同问题：R2T2 的稳定前缀决定哪些词可提交，X-ASR 的增量状态决定哪些计算可以不重做。官方 GGUF 示例的 160 ms chunk 只是送入或查询的节奏，官方 README 把 GGUF 的缓存复用与后缀验证列为后续工作。
- 推论：不能指望把预览步长调短就得到 X-ASR 式的持续上屏，必须先弄清每一轮到底花在哪里。

### 3.2 一轮推理的计算链

PCM → Log-Mel → 卷积 → 音频 Transformer → 投影 → 解码器前填 → 逐词元生成。

前填依次处理模板头、音频嵌入、模板尾与已确认文本。任一较早的音频嵌入变化，其后的解码 KV 都依赖变化后的输入。相比已确认文本的词元数，音频位置要多得多。编码、前填、生成在一次推理内串行，采集与推理并行。

### 3.3 分项计时：热点在哪里

| 场景（K40） | 编码 | 前填 | 生成 | 说明 |
| --- | ---: | ---: | ---: | --- |
| 首轮 1.2 秒音频 | 0.85–0.90 秒 | 1.9–2.2 秒 | 0.53–0.56 秒 | 特征准备与分词通常小于 3 ms |
| 10 秒夹具的 6.5 秒定稿段 | 约 3 秒 | 约 5.3 秒 | 约 1.1 秒 | 前填最大 |
| Q-A06，3.08 秒定稿段 | 4.14 秒 | 2.60 秒 | 0.92 秒 | |
| Q-E08，16 秒定稿段 | 14.82 秒 | 8.43 秒 | 6.51 秒 | 编码约占该轮 29.79 秒的 50% |

独立程序固定 16 秒 PCM、4 线程、固定 CPU 亲和性，进一步拆分：

- **编码。** R2T2 GGUF 卷积 5.78 秒、Transformer 与投影 9.45 秒，合计 15.17 秒。同一片段 Qwen3-ASR 的 ONNX 路径为 2.49 秒，约 6.1 倍差距包含计算图、精度和 CPU 内核实现，当时未分别量化。
- **前填（冷路径）。** 合计 9.81 秒，其中 221 个音频位置 7.30 秒，64 个模板尾和文本位置 2.18 秒，9 个模板头位置 0.33 秒。音频是前填的主要热点。
- **边界成本。** 7.99 秒与 8.00 秒输入的帧数相差一帧，就会多触发一次窗口前向，额外 0.91–1.10 秒。16 秒同理。

### 3.4 为什么每轮都在重算：输入在变

预览每隔约 2 秒触发一次，理想情况下，已完成的音频窗口和对应 KV 可以复用。实测发现输入并不稳定：

- **尾部反射填充。** STFT 末端使用反射填充，音频延长后，尾部附近的帧依赖后续样本。8.00 → 8.02 秒时首窗只有第 799 帧变化，原音量样本有 128 个 Mel 值变化。
- **补零区被真实音频填入。** 7.10 秒的预览只有 711 个有效帧，另有 89 帧补零。
- **全局 Log-Mel 下限。** 固定版本的 llama.cpp 先用当前音频全段最大值归一化 Mel，再切分窗口。后面更长或更响的音频会改变已完成窗口的输入。将前 8.2 秒衰减 36 dB 后，同一组截点有 60,740 个值变化。

用回放原始字节独立复跑 Q-E08 从样本 174400 开始的首窗：

| 同一段音频的截点 | 已有音频内部变化 | 尾部反射变化 | 原补零区变化 | 首窗比对 |
| --- | ---: | ---: | ---: | --- |
| 7.10 → 16.00 秒 | 56 | 256 | 11,392 | 失效 |
| 8.00 → 8.02 秒 | 0 | 128 | 0 | 失效 |
| 8.02 → 9.60 秒 | 59 | 0 | 0 | 失效 |
| 9.60 → 16.00 秒 | 0 | 0 | 0 | 命中，可复用 104 个音频位置和 9 个模板头位置 |
| 10.40 → 16.00 秒 | 0 | 0 | 0 | 命中 |

结论：7.10 秒预览到 16 秒定稿的 11,704 个变化值中，11,392 个来自新增真实音频填入原补零区，其余来自尾部反射和全局下限。复用与否必须按归一化 Mel 的逐位一致性判定，不能只看窗口时长。

### 3.5 实时回放中的实际命中率

隔离包每 100 ms 供帧，覆盖 10.053 秒混说、关闭 VAD 的 20.106 秒重复混说、连续听写 Q-E08、Q-E05 与 S-E10（后三者回放旧策略和 V3），共 8 组：

- 共 38 轮原生推理，音频位置累计前填 42.00 秒，模板与文本位置累计前填 10.45 秒，均包含被中断的批次。
- 11 轮预览被中断：VAD 边界 6 次、16 秒硬窗口 2 次、音频结束 3 次，合计用掉 16.32 秒编码、8.14 秒前填和 0.59 秒生成。
- 只有 3 轮比对的前后首窗张量都达到 800 帧，其中 2 轮命中。其余多为窗口仍在增长、分段后缓存重置，或在首窗计算完成前就被中断。
- Q-E08 的 V3 回放中，16 秒段定稿前只保留 9 个模板头位置，221 个音频位置前填写入约 4.48 秒，模板与文本再用约 0.82 秒。
- 有足量 PCM 与已算出 KV 是两个时刻：串行推理不一定及时完成首窗，这决定了后来的调度实验为何失败（见第 4 节）。

### 3.6 根因小结

| 层次 | 根因 | 证据 |
| --- | --- | --- |
| 计算量 | 音频编码与音频位置前填占大头，CPU 内核与图实现比 ONNX 路径慢约 6 倍 | 3.3 节分项计时 |
| 增量性 | 活动窗口的 Mel 因反射填充、补零和全局归一化不断变化，窗口缓存难以命中 | 3.4 节失效表 |
| 调度 | 过时预览占用串行推理，定稿要等；首窗完成时刻与定稿边界不对齐 | 3.5 节中断统计 |
| 质量边界 | GGUF 的边界 STFT 与卷积补齐使有效位置（221 对 208、78 对 65）与官方参考不一致 | 第 4 节编码器对照 |

这四层各自有不同的解法，也各有不同的风险，后面的方案按层次逐项验证。

### 4.2 采用的方案

**A. VAD 分段与定稿抢占。**

- 做法：采集达到 VAD 分段、16 秒兜底窗口或 EOF 时递增轮次并中断过时预览；定稿优先，已上屏的确认前缀和全部尾部 PCM 保留。音频投影的当前分块结束后响应中断，前填与生成也检查中断。预览按新增音频每 80 ms 约一个 token，限制 20–64 个；首轮约 1.2 秒音频触发，后续间隔至少覆盖上一轮预览耗时的两倍。窗口封口前不足或等于 2 秒时跳过新预览。
- 实测：20.106 秒重复混说停录到定稿 34.188 → 23.382 秒。长句对照中，仅启用 ARM 优化时，15.4 秒的预览消耗 7.31 秒后被固定窗口取消，期间未生成 token，加入跳过规则后这类空耗被消除。Q-A06 停录到定稿 9.92 → 5.83 秒，Q-E08（33.39 秒）68.46 → 33.44 秒。
- 代价与风险：分段带来接缝（「星期三昨天」连写）。预览间隔取一倍时，10 秒夹具的第二次预览在 VAD 定稿前白算约 2.6 秒且无文本，改为两倍后跳过了该轮。

**B. ARM CPU 变体与矩阵乘法内核。**

- 做法：arm64 日常包打包 llama.cpp 的 CPU 变体，加载前由 ggml 校验指令集并注册可用变体，K40 实际加载 ARMv8.2 点积与 FP16 变体；再启用 `GGML_LLAMAFILE`。
- 实测：K40 固定 16 秒输入、同一计算图，独立编码中位数 15.07 → 12.00 秒（默认 14.92 / 15.21 秒，启用后 11.62 / 12.37 秒）。长句 16 秒窗口 46.33 → 29.79 秒，前填 21.49 → 8.43 秒，音频编码 15.06 → 14.82 秒。
- 代价：加载与预热 7.97 → 9.89 秒，加载时峰值 RSS 2.16 → 3.06 GiB。
- 结论：已进入日常 arm64 构建。16 秒编码 12 秒仍远高于 5 秒的分项目标，因此还需要别的手段。

**C. 精确复用音频嵌入与解码器 KV。**

- 思路来源：`audio.cpp` PR #696 的做法，缓存已完成窗口的嵌入，逐位比较判定失效，保留模板头与不变音频的 KV。
- 做法：只有归一化 Mel 的尺寸与内容完全相同，才复用对应音频嵌入。解码器只保留因果提示中输入和位置连续匹配的 KV，重算变化后的上下文与生成 logits 所需的末段。全局 Mel 归一化基准可能随新增语音改变，旧窗口因此每次都要重新比较。上下文位置固定预分配 2048 个，避免跨 512 位置容量分档时整段重填。
- 电脑对照（Windows AVX2、社区 GGUF、同一 CLI，关闭 → 开启复用）：Q-E08 33.39 秒的音频结束到定稿 46.13 → 10.03 秒，累计前填 50.85 → 24.03 秒；16 秒截段 8.57 → 2.42 秒；前 8.5 秒降低 36 dB 的样本 47.14 → 19.61 秒，且触发两次缓存失效。
- K40 实测（修改前后单次实时回放）：

| 夹具 | 首字 | 停录到定稿 | 转写对比 |
| --- | ---: | ---: | --- |
| 5 秒中英截段 | 3.25 → 3.13 秒 | 4.64 → 4.10 秒 | 正文一致 |
| 5 秒弱起声截段 | 3.26 → 3.12 秒 | 4.75 → 4.09 秒 | 空格有差异，词语一致 |
| 10.05 秒中英混说 | 3.28 → 3.25 秒 | 8.17 → 4.97 秒 | 逐字一致，保留末尾「星期三」 |
| 20.11 秒重复混说 | 3.28 → 3.13 秒 | 7.80 → 5.85 秒 | 标点有差异，两遍关键词完整 |

- 正确性用例：同一音频复用、同长度但不同内容必须重新编码、冷热定稿字节一致，均在 K40 隔离包通过（`r2t2ReusesIdenticalAudioAndInvalidatesChangedAudio`，本次会话再次运行 OK, 1 test）。
- 结论：收益取决于特征是否一致、首窗是否在抢占前实际算完。连续听写长段没有受益，甚至略慢，该问题留到第 7 节。

**E. ONNX 编码器原型。**

- 做法：用同一 R2T2 音频塔权重（官方检查点 `d07b4a593610c16074cfc941fba052a7a12eeda3`，397 个张量）导出卷积与 Transformer／投影两个 ONNX 图。卷积按官方规则凑齐形状，每个 800 帧窗口进入 Transformer 前只保留有效位置。动态 INT8 只量化 Transformer／投影的常量权重矩阵乘法，卷积维持 FP32。
- Windows 验证（四线程，预热一次，计时四次中位数）：16 秒窗口 GGUF 668 ms、FP32 443 ms、INT8 254 ms；5 秒弱起声 230 / 144 / 88 ms。FP32 的 7 个样本全部通过逐元素容差检查，最终嵌入相对 L2 误差最高 4.2e-6。
- K40 真机（NDK 29 独立程序，四线程，亲和性 0x93）：

| 输入 | 当前 GGUF | ONNX FP32 | ONNX 动态 INT8 |
| --- | ---: | ---: | ---: |
| Q-E08 16 秒定稿窗口 | 9.50 秒 | 3.96 秒 | 2.30 秒 |
| Q-E08 5 秒低音量截段 | 3.34 秒 | 1.25 秒 | 0.76 秒 |

- 两版 ONNX 都达到「16 秒编码低于 5 秒」的分项指标。加载时间 5.47 / 4.23 / 1.40 秒，编码进程峰值 RSS 2.84 / 1.31 / 0.47 GiB。GGUF 进程同时加载了文本模型，ONNX 进程只加载编码器，内存与加载值不能代表完整会话。
- 质量问题：16 秒样本两版 ONNX 都少了 GGUF 保留的「负责」，INT8 另改坏截段开头。5 秒截点两版都少了「语音」，补入 0.2 秒真实后续音频后恢复。INT8 的 6 秒截点少了「自动」，短口令「发送」的嵌入误差达 24.0%。
- 录音中复用编码（Windows 回放 Q-E08 前 16 秒）：「完整窗口 + 100 帧卷积块」两级复用的输出与全量重算逐元素相同。FP32 累计 1,952 → 1,077 ms，定稿轮 444 → 174 ms。INT8 累计 1,162 → 539 ms，定稿轮 258 → 82 ms。前提是把 Mel 计算批次固定为 100 帧，否则整段 CPU 特征提取约 1.2e-7 的浮点差异会让窗口键全部失配。
- 接入 K40 会话回放（10.053 秒混说）：

| 路径 | 首字 | 录音中更新 | 停录到定稿 | 定稿 |
| --- | ---: | --- | ---: | --- |
| GGUF，2 秒步长，三次 | 2.84–3.06 秒 | 第二批 5.59–5.70 秒 | 4.06–4.30 秒 | 三次逐字一致 |
| ONNX FP32 | 3.58 秒 | 9.12 秒出后半句首词 | 2.41 秒 | 大小写和标点变化 |
| ONNX FP32 加卷积块缓存 | 3.50 秒 | 8.84 秒 | 2.35 秒 | 大小写和标点变化 |
| ONNX 动态 INT8 | 3.40 秒 | 9.10 秒 | 2.29 秒 | 大小写和标点变化 |

- 结论：ONNX 定稿更早，但 1.2 秒输入没有产生可发布正文，首字推迟。5 秒低音量起声夹具中 FP32 定稿漏掉英文 `is`。FP32 两次单轮回放停录差仅 56 ms，缓存收益无法从运行波动中分离。回放进程同时持有 GGUF 音频投影，GGUF 峰值 RSS 3.30–3.39 GiB，FP32 为 4.27–4.33 GiB，INT8 为 3.66 GiB。**编码器继续采用 GGUF，ONNX 仅作原型保留**，两套实验路径已从产品代码移除。

**F. 更短预览步长。**

- 假设：把常规预览步长由 2 秒缩到 1.5 / 1 秒，录音中的出字间隔会变短。首轮仍从 1.2 秒开始，窗口末 2 秒仍跳过预览。
- 实测（K40，GGUF）：10.053 秒混说中，2 秒步长的第二批文字在 5.59–5.70 秒出现，1.5 秒为 4.73 秒，1 秒为 4.75 秒，1 秒没有进一步提前。代价是低音量截段定稿 3.70 → 3.86 秒，20.11 秒重复混说 4.57 → 5.17 秒。连续听写 Q-E08 在 V3 同策略下，2 秒与 1.5 秒的最长无更新分别为 11.01 和 11.95 秒，停录到定稿分别为 6.97 和 9.86 秒，1.5 秒还在第二项开头出现不同的误识别。
- 原因：预览要等串行的编码与前填结束才能再推进，缩短触发步长不能缩短每轮计算本身。
- 结论：保留 2 秒。

**G. 更短的编码窗口。**

- 假设：PR #696 的文档用 4 秒窗口，窗口越短，已完成窗口越容易被复用，单轮编码也更短。

| --- | ---: | ---: | ---: | ---: |

- 交错复测：按 8 → 4 → 4 → 8 秒回放同一长段，停录到定稿依次为 14.51、17.22、20.66、20.66 秒，最长无更新为 11.54、11.47、18.30、18.57 秒，四次完成窗口缓存命中均为 0。各次开始时电池温度为 35.0、35.7、36.5、36.7 °C，CPU 频率未固定，开测前标准包同段定稿为 6.53 秒，说明整场时延随运行条件和抢占时序变化，不足以把差异归因于窗口。

- 结论：保留 8 秒，撤回窗口实验。若继续优化，先在固定 PCM 截点逐轮记录缓存未命中的原因，区分 Mel 变化、预览抢占与 VAD 分段重置。

**H. 前填线程、文本 KV 复用、合并前填批次。**

- 线程：K40 固定 8 秒输入，允许全部八核，按 4 → 6 → 8 → 8 → 6 → 4 交错。四线程两次 2.23–2.24 秒，六线程 3.05–3.13 秒，八线程 2.56–4.11 秒，输出一致。保留四线程。
- 文本 KV 复用：只在音频完全不变时，精确复用 55–56 个已确认文本位置，只重算后缀与产生 logits 的末词元，前填由 1.00–1.23 秒降到 0.09–0.14 秒。相同、追加、改写、缩短前缀以及增加 100 ms 音频后的输出与原路径逐字节一致。但已有短句、长句和 16 秒硬窗口回放里，定稿音频与先前成功前填的音频没有可利用的完整命中，实时回放缺少这种机会，暂缓接入。
- 合并批次：把音频嵌入与文本词元合为一批，六个固定截点输出一致，耗时收益不稳定，16 秒截点还超出原型的单批覆盖范围，暂缓接入。
- 以上原型只在独立程序运行，产品代码未改，日志与原型在本机 `%TEMP%\sayin-r2t2-prefill`。

### 4.4 编码精度对照：为什么不能直接换编码器

逐级对照当前固定版 llama.cpp 与官方参考（`qwen-asr 0.0.6` 音频编码器，SDPA 显式传入等价于官方 vLLM 的分窗注意力掩码），层级为 Mel、三层卷积、卷积线性映射、Transformer、最终投影。

- 完整 8 秒窗口内，Mel 相对 L2 误差低于 2e-6，投影低于 0.07%，两条路径在正常窗口内是对齐的。
- 7.99 秒边界样本的前 799 帧仍对齐，但当前 GGUF 把额外的反射帧用作第 800 帧，参考则把该位置补零，该窗口投影的相对 L2 误差升至 29.1%。
- 当前 GGUF 保留恰好 8 秒或 16 秒边界上的额外 STFT 帧，并让补齐到 100 帧卷积块后的全部位置参与 Transformer。16 秒输入因此产生 221 个音频位置，参考为 208 个；5 秒输入为 78 对 65。
- 3.24 秒样本的有效卷积线性输出相对 L2 误差只有 0.043%，但 Transformer 继续处理填充位置，最终投影误差达到 32.8%。在 Transformer 前只传有效位置后，使用原 GGUF 卷积结果的投影误差降到 0.052%。仅在输出处删掉尾部位置无法恢复前面位置的注意力结果。
- 电脑端把原 GGUF 嵌入从外部接口送回同一解码器，16 秒片段转写逐字一致，说明解码器接口本身没有问题。保持同一份 ONNX Mel 输入，把单次 16 秒编码改为两次 8 秒编码，嵌入相对 L2 差 8.35%，转写由「并二十百定」恢复为 GGUF 基线的「并二次绑定」。再以第三次前向补齐到 221 行，在这条用例上没有继续改变转写。这说明前端对齐除了嵌入维度，还要核对编码窗口。
- 在 K40 上用 Qwen ONNX 预先计算的嵌入交给同一 R2T2 解码器，百分比、手机号和「发送」的正文一致，但 16 秒片段末尾由「接下来由各自负责」变成「接下来由各自」，低音量起声片段少了「语音」，局部预览也有差异。
- 补测 `refer/voice` 的 6 个片段：短词 Q-E02、句中停顿 Q-E05、紧贴尾音结束 Q-E10 正文一致；中英混说 Q-C17 两条路径都错读 API、JSON；Q-E08 前 1.2 秒降到 20% 振幅后截取 5 秒，原 GGUF 保留「语音」，ONNX 漏掉。该样本短于单个 8 秒窗口，分窗不会改变它的嵌入，因此差异来自截点与有效帧口径。

结论：换一个更快的编码器不是纯性能问题，它同时改变有效位置、边界帧和转写，必须同时通过质量验收。完整句尾与流式部分结果应分别验收，单个截点 0.2 秒的差异不足以确定产品等待时长。

### 4.5 正确性保障与证据边界

- 缓存命中只由归一化 Mel 的逐位一致性决定。设备用例覆盖同音频复用、同长度不同内容重新编码、冷热定稿字节一致。
- 每轮优化前后都执行 `scripts/gradle.ps1 :app:testDebugUnitTest :translation:testDebugUnitTest :app:lintDebug :app:assembleDebug`、`python scripts/check_i18n.py` 与差异检查。应用 JVM 测试由 221 项增至 238 项，预览调度新增用例在旧规则下捕获到多余预览而失败，恢复新规则后通过。
- 实验代码均在隔离包内进行，结束后恢复并重新构建标准隔离包与日常 Debug。日常包只用 `adb -s dc39c31d install -r` 覆盖安装，首次安装时间保留，主界面冷启动成功。
- 以上全部为预录 PCM 按实时节奏供帧的回放，不含真人麦克风、Compose 实际绘制延迟、长时功耗与目标延迟分位数。热状态与 CPU 频率未固定，跨批次波动不能全部归因于单项改动。

### 5.2 V3 策略的最新回放（本次会话）

同一 K40 隔离包、同一批预录 PCM，对照旧策略与 V3：

| 夹具 | 指标 | legacy-policy | v3 |
| --- | --- | ---: | ---: |
| Q-E05（句中 1.5 秒停顿） | 停麦后定稿 | 1498 ms | 398 ms |
| Q-E05 | 录音中有文字 | 否 | 是 |
| Q-E05 | 最终转写 | 我需要想一想。 | 我需要想一想，还是明天再决定吧。 |
| S-E10（弱声，手动结束） | 停麦后定稿 | 1596 ms | 1639 ms |
| S-E10 | 最终转写 | 好的，我现在就发给你。 | 好的，我现在就发给你。 |
| Q-E08（38.4 秒，手动结束） | 停麦后定稿 | 2697 ms | 89 ms |

解读：

- Q-E05 中旧策略在 1.5 秒停顿处就封段，丢失后半句；V3 完整保留，且停麦后定稿快约 4 倍。
- S-E10 手动结束且无尾部静音，两版本时延与转写一致，符合预期，该路径没有收益也没有回退。
- Q-E08 的 89 ms 说明本次回放中定稿轮命中了完整缓存，不能外推为长句的普遍表现，同一输入跨批波动可达 5–12 秒（见 5.3）。

### 5.3 体验目标的达成情况

| 目标 | 当前状态 | 证据与差距 |
| --- | --- | --- |
| 录音中出字 | 大部分达成 | 混说、长句、Q-E05 均在录音中出字；短句 S-E10 仍在停录后才首次出字 |
| 首字 | 约 2.3–3.8 秒 | X-ASR 对照 1.7 秒，差距约 1–2 秒 |
| 持续增量上屏 | 未达成 | Q-E08 录音中最长无更新仍有约 10–12 秒，隔几秒分批出字 |
| 停录到定稿 | 短句约 4–5 秒、混说约 4.3–5 秒 | 同一批 X-ASR 为 0.285 秒；长句 5.5–13.6 秒，波动大 |
| 16 秒编码低于 5 秒 | 产品未达成 | 产品 GGUF 路径约 12 秒，ONNX 原型 2.3–4.0 秒但质量不过关 |
| 准确率不退化 | 基本保持 | 缓存复用逐字一致；长句「第二是本地」「第三是」错识别在各路径、上游对照中均存在 |

### 5.4 效果判断

1. **定稿等待下降明显。** 混说由 8.17 降到 4.97 秒，Q-E08 由 68.46 降到 33.44 秒，Q-E05 在 V3 下降到 398 ms。这些都来自「少做无用功」：预览抢占、跳过窗口末尾预览、复用不变输入。
2. **编码本身没有数量级的改善。** 产品路径的 16 秒编码只从 15.07 降到 12.00 秒，大幅提速只在 ONNX 原型上出现，但原型没有通过质量验收。
3. **长句仍是短板。** 连续听写的缓存收益不稳定，最长无更新和停录到定稿受抢占时序、温度和频率影响，波动大于多数单项优化带来的差值。
4. **与 X-ASR 仍有明显差距。** 在同一批预录回放中，X-ASR 的首字与定稿都明显更快，这是架构差异：R2T2 的活动窗口双向注意力使已有位置的编码随新音频改变。

## 6. 思考思路与方法论

### 6.1 先拆体验，再拆计算

用户说的「慢」包含三个互相独立的体验：录音中看不到字、持续上屏的节奏、停录后的等待。它们对应的计算路径不同，不能用一个指标概括。因此先固定计时口径（第 1.2 节），每个数字都说明起止点，再逐项对应到预览链路、调度和定稿链路。

### 6.2 先看占比，再决定优化什么

没有先动代码，而是先做分项计时：编码、前填、生成各占多少，音频位置和文本位置的前填各占多少。结论是音频编码与音频位置前填是大头，文本生成不是。这直接排除了「减少生成 token」「换更小的解码器」这类方向，把后续假设限定在三类：算得更快（内核、后端、编码器）、算得更少（复用）、算得更巧（调度）。

### 6.3 把「能不能复用」当作可验证的问题

复用的前提是输入不变，而输入是否不变不能靠推断。因此专门做了失效定位：逐位比较同一段音频在不同截点下的 Mel，把变化值归因到「已有音频内部」「尾部反射边界」「原补零区」三类（第 3.4 节）。这一步把「缓存命中率低」从一个现象变成了有来源的解释，也说明只看窗口时长判断复用是错的，必须以归一化 Mel 的逐位一致性为准。

### 6.4 每个方案都带着否定条件

每个实验开始前就明确什么结果会让它被撤回：转写出现退化、首字被推迟、无法从运行波动中分离出收益。这使得多个看起来有吸引力的方案能被干净地放弃：

- ONNX 编码器编码快 2–4 倍，但首字推迟、弱起声漏词，被否定；
- 更短步长和更短窗口局部有收益，交错复测不能重现，被否定；
- 等待首窗的调度理论上合理，实测让最长无更新从约 10 秒变成 15–19 秒，被否定。

### 6.5 控制变量与交错复测

设备温度和 CPU 频率会随连续运行变化，单次对照不可靠。采取的做法：

- 同一设备、同一 PCM、同一供帧节奏、同一模型文件，仅切换一项；
- 多个配置按 A → B → B → A 交错回放，而不是各跑一批；
- 记录开测电池温度，并明确频率未固定；
- 对跨批波动大的结果只报告范围，不把差值归因于单项改动。

窗口实验是典型例子：单次对照显示 4 秒窗口更快，交错后同一配置自身就波动了 14.51–20.66 秒，原结论不成立。

### 6.6 质量与速度同时验收

速度优化不能以转写退化为代价，所以每个方案都同时看关键词（Monday、星期三）、弱起声、尾词、数字、短口令和已知易错句。缓存复用要求输出与冷路径逐字节一致，编码器替换要求逐元素对照加转写对照。这也是 ONNX 与 Q8_0 被否定的主要原因：速度收益没有覆盖质量风险。

### 6.7 区分「有数据」与「有结论」

文档刻意区分三种状态：

1. 已进入产品并有前后对照的改动；
2. 只在独立程序或隔离包验证的原型；
3. 已撤回的实验及撤回原因。

预录 PCM 回放不等于真人麦克风，识别回调时间不等于绘制时间，单次最快值不等于稳定表现。这些边界在每一节都保留，避免把有限的证据说成整链路验收通过。

### 6.8 遵循项目工程规则

- 根因优先：不通过加特殊判断绕过现象，而是追到 Mel 失效、调度、编码内核三个层次；
- 最小 Diff 不是目标：撤回实验时直接恢复原实现并重新构建，不保留兼容分支或开关；
- 完成标准是验证通过：每轮改动都执行 JVM 测试、lint、双语检查，并在设备上运行同音频复用、变更音频失效等正确性用例；
- 日常包只用 `install -r` 覆盖安装，实验只在隔离包 `seeyuer.sayin.imagetest` 中进行。

### 6.9 踩过的坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 窗口缓存全部失配 | 整段 CPU 特征提取随计算尺寸有约 1.2e-7 浮点差异 | 把 Mel 计算批次固定为 100 帧 |
| 复测被打断 | 另一条仪器化命令启动，系统记录 `start instr` 强制停止 | 上一条完全退出后再复跑 |
| K90 后台首跑全部停住 | 测试进程线程进入 `do_freezer_trap` | 使用重新启动的前台测试进程 |
| Vulkan 预热报错 | 整数点积配置触发 256 token 采满 | 仅关闭整数点积后可回放，无稳定收益 |
| 把 4 秒窗口收益当成整场收益 | 单轮命中，交错复测未重现 | 以交错结果为准，撤回实验 |
| 把 89 ms 当成长句普遍表现 | 该次定稿轮恰好命中完整缓存 | 同时报告跨批范围 5–12 秒 |

## 7. 未决问题与后续验证顺序

### 7.1 未决问题

1. **持续上屏仍未达到 X-ASR 水平。** Q-E08 录音中最长无更新仍约 10–12 秒。预览要等串行的编码与前填结束才能再推进，缩短步长无法缩短单轮计算。
2. **长句定稿波动大。** 同一 Q-E08 在标准包上停录到定稿曾测得 5.47–13.62 秒，来源包括首窗是否在抢占前算完、温度和 CPU 频率。89 ms 的结果只是一次完整缓存命中。
3. **编码仍是最大单项。** 产品 GGUF 路径 16 秒编码约 12 秒。ONNX 原型 2.3–4.0 秒，但存在弱起声漏词、尾词丢失和首字推迟，不能直接接入。
4. **边界帧与有效位置与官方参考不一致。** GGUF 的 16 秒音频产生 221 个位置，参考为 208；5 秒为 78 对 65。修正需要同时核对编码窗口、边界 STFT 和转写。
5. **长句错识别。** Q-E08 的「第二是本地」「第三是」在当前 GGUF 和部分上游对照中都会出错，需要分开对照模型权重、提示与截点、编码输出和已提交前缀，并记录每个错词首次出现在哪一轮。
6. **K90 Pro Max 记录滞后。** K90 数据早于最近的 K40 首窗实验，且整机通信回归曾有 Keystore 失效等未放行项，与 R2T2 本身无关但需单独处理。
7. **证据边界。** 全部数据为预录 PCM 回放。真人麦克风、Compose 实际绘制延迟、长时功耗、目标延迟分位数（p50/p95/p99）均未测。

### 7.2 后续验证顺序

1. 固定同一段音频的 1.2 / 3.2 / 8 秒预览截点和 16 秒定稿输入。
2. 分开计时 Mel、卷积、Transformer 与投影、音频前填、文本前填和生成。
3. 记录首窗实际完成的时刻、定稿复用的位置数、转写与资源峰值。
4. 逐轮记录缓存未命中原因，区分 Mel 变化、预览抢占和 VAD 分段重置。
5. 优化确认有效后，回到前台隔离包的 100 ms 供帧回放，覆盖短句、持续讲话、弱起声、响度突变、VAD、手动停录和硬窗口。
6. 记录设备热状态与频率，报告首字、最长无更新、定稿与质量，再判断是否值得接入日常包。
7. 编码器方向：先对齐有效位置与边界帧，再评估 ONNX 或其他后端，质量验收通过后才评估整条链路。
8. 最后补真人麦克风、绘制延迟与功耗验收。

### 8.5 当前结论

R2T2 这条链路的瓶颈已经定位清楚：**编码是最大单项，缓存能否命中决定定稿是否即时，短步长预览受串行计算限制**。已落地的两项优化（VAD 分段与抢占、精确音频／KV 复用）在 K40 上可复现，质量未退化；编码器替换方向有原型数据但未达到质量门槛。下一步的唯一有效入口是按 7.2 的固定输入重跑分解计时，先把「编码时间」这一项单独压下去，再谈体验对齐 X-ASR。
