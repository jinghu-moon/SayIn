# 19 · 已接收但未落字：队列过期与原因提示修复

日期：2026-11-13。

## 现象与证据

用户反馈手机发送的文字已经出现在电脑端记录中，但没有输入到当前光标。只读检查现有生产账本，未解密或导出正文：第一条请求为 `held / foreground_guard_failed`，后两条为 `accepted`，接收控制未暂停。第一条已经超过接收后 30 秒，仍阻塞后续请求。

旧版仅保存通用前台检查错误码，无法事后断定第一条究竟因为声达自身在前台、管理员目标、修饰键、会话状态还是其他平台检查失败。不能把“收到文字”当成“已提交输入事件”。

## 根因

协议 01 要求：有效的挂起队首必须阻塞后续请求；接收后最多 30 秒，挂起、断线及人工确认均不能重置有效期。

旧实现有三个缺口：

1. `prepare_next` 在检查期限之前直接返回挂起队首，导致该队首永远不会过期。
2. 协调线程无限等待下一条命令，没有主动过期调度；无用户操作时无法推进终态和通知。
3. `release` 为请求重新分配 30 秒期限，延长了旧文字的执行窗口。

手机与电脑截图曾显示不同状态，因此另加 WSS 推送和 Android 持久化回归；没有证据证明旧截图中的差异由另一个传输缺陷引起，不据此修改协议或添加重复发送。

## 实施

- 协调线程在命令处理前及空闲时检查单调时间期限，空闲检查间隔 250 ms。普通请求仍立即唤醒线程，不等待这个间隔。
- 只遍历有界的内存活跃期限集合，在同一 SQLite 事务中把到期的 `accepted/held` 改为 `expired`，释放待执行载荷和队列配额。没有全量历史扫描，没有删除正文历史。
- 提交后通知界面和传输层，再调度仍有效的后续请求。有效挂起队首仍阻塞后续，未绕过顺序约束。
- 人工 release 保留原期限。开始执行前再次核对期限；已开始执行和 `uncertain` 不被定时器改判为过期。
- 重启恢复的旧请求没有可信的单调时间期限，在恢复调度时过期；不会把旧文字输入到重启后的新光标。显式暂停及不确定结果仍须按原规则处理。
- Windows 前台预检细分为 `receiver_focused`、`target_missing`、`elevated_target`、`modifier_held`、`session_unavailable`；未知平台错误保留通用码，不泄露平台细节。进程 ID 不可用与声达自身在前台分开处理。
- 桌面最近一条、桌面历史和手机历史使用资源展示具体原因、排队与过期含义，覆盖简体中文和 English。原文、配对、密钥和收据身份保留。

输入路径继续使用独立串行输入线程、持久执行标记和终态提交后回执。不抢焦点、不锁定应用、不增加逐条桌面确认、不追加 Enter，不自动重试挂起或不确定的旧文字。

## 验证

新增回归包括：挂起及暂停中的请求都到期；release 不续期；过期后释放待执行配额而保留历史；执行中及不确定请求不被定时器改判；没有查询或界面刷新时，挂起队首先过期，然后执行仍有效的后续请求；前台原因映射及双语展示不暴露内部错误。

WSS 测试使用固定证书 TLS 1.3、独立配对与假输入 adapter，验证服务器主动推送 `accepted → held → expired`，随后有效请求执行一次。Android 回归在独立 host/device 和存储命名空间中，验证实际手机收到 `held` 原因、收到主动 `expired` 回执并持久化，重连和 repository 重建保留状态；不触碰用户配对和 Outbox。

原有 GPUI 核对恢复测试相应加强：重启后旧请求应过期，正文保留且无执行时间，不再断言它永远占用 pending；不确定结果仍存在，恢复操作没有把旧文字判为已输入。

检查日志及最终部署状态见 [验收记录](research/19-input-queue-verification-2026-11-13.json)。工作区测试、Clippy、构建、包限定格式检查、双端 i18n/依赖检查、Android Lint/单元测试及真机仪器化测试分别留有日志。

最终桌面工作区 90 项测试通过，Clippy `-D warnings`、构建、格式、i18n/依赖检查通过；Android Lint、单元测试和 Debug 构建通过。手机仪器化运行中前 6 项数据/协议/通信测试通过，包含本次新增的主动挂起、过期回执及重连持久化断言。随后 MIUI 拒绝测试 Activity 的后台启动（`Abort background activity starts`），整套 11 项未完成；正常启动应用后重试仍阻塞，停止测试后恢复正常应用。未更改系统后台启动权限，不能声称本轮全部手机 UI 测试通过。

新版桌面端已替换并以可见主窗口启动，手机安装包保留数据更新。用户明确退出旧程序后保留了暂停状态；本次启动时旧请求尚为重启待核对状态，它们在恢复调度时按无可信期限过期，不会补打。测试前如显示暂停，先启用输入；公用网络如要求本地会话授权，先在电脑允许本次网络使用。

以上通信与调度测试使用假输入，不能作为真实目标软件已经落字、输入延迟或前台竞态消除的证明。实际用户光标验收仍按以下步骤进行。

## 更新后验收步骤

1. 确认桌面端网络服务运行、手机已连接、输入处于启用状态。公用网络沿用已有本地会话授权，无需修改 Windows 网络分类。
2. 在普通权限的记事本中新建空白文档，点击正文输入区，保持记事本为前台。接下来只操作手机。
3. 手机发送一条新的、易辨认的文字，例如“光标测试一，收到请落在记事本”。预期直接出现在记事本光标处，不追加换行或回车；手机与电脑最终显示已输入。
4. 切到另一个普通权限编辑器的输入框，再从手机发送一条新文字。预期进入新的光标位置，不需要桌面确认或锁定。
5. 如仍未输入，记录手机和电脑该条请求显示的具体原因；不要反复发送相同旧条。管理员目标请先换普通权限窗口测试，修饰键按下则先松开。

本次更新不补打过期旧消息。此前失败记录的原文继续保留在电脑历史中，需要时可复制后重新确认发送。
