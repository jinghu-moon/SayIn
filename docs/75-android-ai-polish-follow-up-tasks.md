# 75 · Android AI 润色后续任务

父设计见 [73 · Android AI 润色](73-android-ai-polish-design.md)，已有功能与测试证据见 [74 · 实施记录](74-android-ai-polish-implementation.md)。第一批实施进度与未通过项见 [76 · 第一批实施记录](76-android-ai-polish-batch1-implementation.md)；第二批用量与费用见 [77 · 第二批实施记录](77-android-ai-polish-batch2-usage.md)；第三批与真机验收边界见 [78 · 真机验收记录](78-android-ai-polish-device-validation.md)。

已有手动和自动润色、AI 翻译、流式预览、术语表及前后对比。用户已跑通 DeepSeek 润色。当前代码只保存一份服务配置，模型靠手填，近 100 条调用记录只覆盖基础 Token 和耗时，费用缺少可用价目。74 号文档中的厂商实测、ASR 实录和目标应用落字仍需补齐证据。

## 第一批 · 服务配置和模型可选

### 1. 建立现有行为基线

- [ ] 运行 AI 润色、设置状态与自动润色的现有 JVM 测试。用当前手机复测一次 DeepSeek 手动润色，记录协议、实际模型 ID、使用流式与否、耗时和可用的 `usage` 字段。用固定样句，测试记录里只保存脱敏结果。
- [ ] 记录当前保存、切换、自动润色授权、失败保留原稿和显式发送的表现，供完成后对照。

**验收**　能复现当前 DeepSeek 链路，并分别记录 JVM、真机和真实服务各自覆盖的行为。

### 2. 保存多份服务配置

- [ ] 每份配置有稳定 ID，保存服务预设或自定义服务、端点、协议、鉴权、Key 和所选模型，另存当前使用的配置 ID。同一厂商可保存多份。继续使用 AndroidKeyStore 和原子加密存储，删除当前配置后由用户从剩余配置中选用。
- [ ] 在同一 AI 设置页切换、编辑、测试和删除配置。端点、协议或鉴权变化时重新确认 Key。同一绑定内换模型继续使用原 Key。测试连接使用界面明确选定或正在编辑的配置，避免误用其他账号额度。
- [ ] 每次调用冻结配置 ID 和版本。切换、编辑或删除当前配置时撤销旧自动润色授权和旧结果的应用资格。迟到结果归原调用记录，草稿保持用户当前内容。

**验收**　保存 DeepSeek 和一个中转站，重启后切换可恢复各自选定的模型。增删或修改一份配置时，另一份的 Key、端点和模型保持原值。MockWebServer 检查旧 Key 不会发往新端点，切换期间的旧结果不会覆盖草稿。

### 3. 内置 basellm 快照并定期更新

- [ ] 增加发布时生成或核验快照的可重复步骤，内置目录、SHA-256 版本、格式版本、来源和取数时间，保留上游许可。建立官方预设到 basellm 厂商 ID 和区域的明确映射。目录只提供文本模型候选和参考价格。
- [ ] 保存官方服务配置后，注册唯一的 WorkManager 联网周期任务，默认每 24 小时检查。没有官方配置时取消该周期任务。服务页提供手动刷新和上次成功检查时间。两种入口共用一次刷新，实现 `ETag` 条件请求和有界下载。
- [ ] `304` 只更新检查时间。新目录通过 UTF-8、大小和结构校验后原子替换缓存。下载或校验失败继续使用当前目录。应用升级后按 §5.9 的随包版本规则选择缓存。刷新请求只访问固定公开 HTTPS 目录。

**验收**　首次离线可读随包目录，覆盖 `200`、`304`、坏缓存、非法目录、写入失败和升级切换。手动与后台同时触发时只发一次请求，捕获的目录 GET 无服务 Key 或用户数据。用测试调度器验证任务唯一性，再在真机记录系统实际执行结果。

### 4. 模型搜索、手填和中转站列表

- [ ] 将模型输入框改成可搜索也可手填。官方服务从本地目录提供候选，始终保留当前已保存的模型。刷新目录、候选下架或返回空列表时，表单仍可用，模型和 Key 不被重置。
- [ ] 自定义服务在支持时，通过同一已确认的服务端点、鉴权和 API 路径获取列表，例如 OpenAI 兼容的 `GET /v1/models`。模型列表请求和付费连接测试独立。返回 401、404、空列表或超时可继续手填。切换服务后丢弃前一个服务迟到的列表响应。
- [ ] 按已验证的端点、协议和准确模型 ID 匹配请求参数。单独检查现有按厂商写入的参数，例如 OpenAI 的 `reasoning_effort`，避免从下拉切到其他模型后仍继承未经验证的字段。官方直连与中转站继续共用现有客户端协议实现，由配置决定请求目的地。

**验收**　离线可搜索官方候选。中转站返回自定义模型 ID 可选择。手填模型保存重启后仍可用。选不同模型时抓取请求并核对参数，由一次用户动作发出的付费 POST 最多一条。

## 第二批 · 用量与计费

### 5. 归一化用量并保存调用记录

- [ ] 对 Chat Completions 与 Anthropic Messages 的普通响应和 SSE 共用同一套用量语义，记录实际回显模型、总输入、总输出、缓存读写与推理分项。校验非负整数、分项关系和溢出。推理 Token 已计入输出时保留为明细，DeepSeek 同义缓存字段只记一次。
- [ ] 按 73 号文档 §4.3 用独立 Room 表按调用 ID 持久化，替换当前 SharedPreferences 的 100 条列表。按配置 ID、用途、模型记录，区分润色、翻译和连接测试。保留耗时、HTTP 状态、终态和已拿到的用量。按设计保留最近 90 天，清空后迟到结果不得复活记录。
- [ ] 覆盖截断、拒绝、取消、超时、进程恢复和结果过期。已知未发送与可能计费的未知调用分别呈现。结果能否应用到草稿由会话判断，用量归原调用结算。

**验收**　普通响应和 SSE 对同一 `usage` 归一结果一致。取消和失败仍保存已经收到的用量，进程中断后显示未知终态，重复完成、同时写入和清空竞态通过测试。

### 6. 接入费率和完善用量页

- [ ] 优先采用已核验的上游单次金额和币种。官方服务的估算使用调用开始时冻结的目录版本和请求时间，再用实际返回模型、计费分项、区域、套餐、档位、币种及时段匹配。使用十进制定点计算，保留单次细精度，汇总后再取整。
- [ ] 中转站金额以该站的已核验上报或独立费率为准。价格和用量无法唯一匹配时显示「未知」，明确上报的零金额显示为零。遇到 basellm 覆盖不了的时段例外，例如未表达的法定节假日规则，保留 Token 并标记费用未知。
- [ ] 用量页提供今日、最近 7 天、最近 30 天，按服务配置、模型和调用用途查看。展示调用量、Token、耗时中位数、各币种金额与未知费用数，标明「服务上报」或「估算」。历史明细保留金额、币种、来源、目录版本和规则标识。

**验收**　固定夹具覆盖区间计价、缓存读写、价格变动、未知和零费用、多币种、同厂商多个账号及中转费率。刷新后老记录金额不变，发起于刷新前的请求沿用当时版本，新调用使用新版本。用真服务返回的用量与公开定价或中转站后台抽样核对。

## 第三批 · 润色质量与真机验收

### 7. 建立固定语料和来源回归

- [ ] 以相同语料复测本地 ASR、豆包云 ASR、输入法、剪贴板和选区。两类 SayIn ASR 默认语音整理，输入法自带语音随 IME 上屏走文本校对，剪贴板用文本校对并保护结构。混合草稿和选区按现有规则，自动润色只覆盖空草稿起步、进入 `KeepDraft` 的本轮 ASR final。
- [ ] 语料覆盖中英混说、专名、数字、日期、否定、命令、代码、链接和表格。分别核对事实保留、赘词删减、结构保护、超时和延迟。用真机验证本地和云端 ASR 的 final、提前结束、取消和断网。若评估豆包 `enable_ddc`，同一组音频对比原识别、识别侧顺滑和现有 LLM 润色，再根据质量、耗时与费用决定是否调整提示词或处理流程。

**验收**　输入法和剪贴板不会触发自动润色，ASR partial 不会发起请求。真实录音能触发符合条件的一次润色。取消或失败保留原文，关键事实和命令在固定语料中保持准确。

### 8. 按真实服务和设备完成验收

- [ ] 用 DeepSeek 回归普通响应与 SSE，然后用千问、OpenAI、Claude 和至少一个实际使用的中转站验证请求参数、实际模型、缓存用量、取消、错误处理与费用来源。有真实账号的服务用短固定样句做小额验证，未取得账号的服务在记录中标为待验证。
- [ ] 在 Redmi K40 上验证保存与切换、离线选择模型、目录刷新、分项用量和历史价格。走通说话页与快捷卡的录音、润色、撤销、显式发送和电脑回执，至少在一个实际目标应用观察文字是否出现，并复测 RTL 翻译显示。分别记录「正在润色」「等待电脑回执」和实际输入结果。
- [ ] 运行 `:app:testDebugUnitTest`、`python scripts/check_i18n.py`、`:app:lintDebug`、`:app:assembleDebug`，用 `scripts/gradle.ps1` 调用 Gradle。每批 Android 改动完成后构建 Debug 并覆盖安装到手机，确认包名、设备和实际启动结果。执行 AI 仪器化 UI 用例并记录结果，系统拦截安装时如实保留未执行项。涉及发送链路时补跑 `scripts/verify_android_transport.ps1 -FullSuite`，并单独记录真实应用落字。

**验收**　每批有修改前后行为对照、命令和真机证据。成功接收回执、实际落字、厂商调用成功和计费准确各自核验。

## 实施顺序

第 1 项作为公共基线。第 2、3 项完成后接入第 4 项。第 5 项可和目录工作同时推进，第 6 项依赖配置 ID、价目目录及用量记录。第 7 项的语料从基线阶段开始收集，第 8 项在每批交付时补齐相应证据。OpenAI Responses 等新增协议按用户实际需要另立任务。
