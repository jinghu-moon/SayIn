# R2T2 K90 Pro Max 调度与线程基线对照

记录时间 2026-11-26 夜。分支 `Gemini/R2T2-optimize`（工作区 `D:/100_Projects/110_Daily/SayIn-R2T2-optimize`），设备 K90 Pro Max `f3ba305a`（Android 17，8 核，电池 33–34 °C）。本文补完上一轮中断的 B 组、C 组与线程基线对照，并给出可复跑入口。K40 与更早的 Windows 记录见 [87 交接](87-r2t2-performance-handoff.md) 与 [88 完整调查](88-r2t2-latency-investigation-full-record.md)。

## 1. 目的与范围

上一轮在 K90 上确认当前 `mmproj-Q8_0 + r2t2_mtmd.inc` 基线的单遍 RTF 已小于 1，但长句仍有 9–10 秒无更新、停录等待 3.7–4.6 秒。本轮要回答三件事：

1. 只把编码窗口从 16 秒改成 8 秒、并加节奏门控（不再每 2 秒无条件重算）能带来多少收益；
2. 完全不预览、只做 VAD/8 秒分段提交，体验是什么样；
3. 新增可配置的编码线程、生成线程数对单遍耗时和端到端体验的影响，4 线程基线是否仍是最优。

## 2. 本轮代码状态

A/B/C/T 组使用 22:00 构建的隔离包执行，D 组回归在默认值改完后于 22:58 重新构建、覆盖安装并复测，P 组诊断与最终默认（前填 8 线程）在 23:44–23:52 之间完成并复装。改动如下（均为工作区未提交状态）。节奏门控与无语音跳过已作为默认行为进入代码（A 组改动），B/C 组通过仪器化 `-e` 传入 8 秒窗、纯分段和线程数；测完 D 组回归后产品默认定为 **16 秒窗 + 编码 6 + 生成 4**，P 组诊断后又把 **前填 8** 定为默认（`DEFAULT_ENCODE_THREADS` / `DEFAULT_GEN_THREADS` / `DEFAULT_PREFILL_THREADS`），仪器化默认值同步引用这三个常量：

- `R2t2Decoder.kt` / `recognizeR2t2`：可配置 `decodeWindowSamples`、`previewStepSamples`、`previewsEnabled`、`pacedPreview`；节奏门控按上一次推理实际耗时抬高最小间隔；VAD 确认整段无语音时跳过解码并返回空结果；默认线程改为 6 / 4；
- `r2t2_jni.cpp`：`encode_threads` / `gen_threads` / `prefill_threads` 可配置；100 帧卷积块级缓存（窗口前段不变时只重算脏块）；尾段文本 KV 复用；
- `SpeechRecognition.kt` / `LocalPcmBuffer.kt`：`noSpeech` 沿采集链路上送。

正确性先于性能：

## 8. 音频前填诊断（P 组）

第 1 节提到的“音频前填比文本前填贵 3–4 倍、修好可把无更新压到 2 秒内”需要先验证。用一个仅在 `SAYIN_R2T2_PROBE` 环境变量下启用的临时探针（诊断完成后已移除）记录每个 decode 批次的音频位置数、文本词元数与耗时，用同一组 20.106 秒回放对照预填线程数：

| 预填线程 | 音频前填 | 文本前填 | 20 s 停录→定稿 | 最长无更新 | 用例耗时 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 4（原默认） | 8.76 ms/位置（478 位置） | 11.49 ms/词元（159 词元） | 0.987 s | 3.075 s | 27.14 s |
| 6 | 6.30 ms/位置（470） | 8.17 ms/词元（158） | 0.939 s | 2.935 s | 25.39 s |
| 8 | 5.55 / 6.17 ms/位置（467/467） | 9.75 / 9.44 ms/词元（158/158） | 0.675 / 0.691 s | 2.808 / 2.817 s | 24.10 / 25.32 s |

结论：

1. **“音频前填贵 3–4 倍”不成立。** 每个音频位置的 prefill（8.8 ms）与每个文本词元（11.5 ms）是同一量级，音频甚至略便宜。此前判断只比较了总时长，没有同时记录位置数与词元数：一轮里音频有 80–100 个位置、文本只有 12–23 个词元，所以音频前填“看起来”是大头，其实是正常工作量。
2. **真正的浪费是前填线程数。** `n_threads_batch` 跟着 `prefillThreads` 走，而默认一直是 4，K90 却有 8 个核。改成 8 后音频前填降约 30–37%、停录等待从 0.99 s 降到 0.68 s、最长无更新从 3.1 s 降到 2.8 s；6 线程居中。已把 `DEFAULT_PREFILL_THREADS = 8` 写进 `R2t2Decoder`，并复跑正确性用例与 10/20 秒回放通过。
3. **单轮成本（默认 8/6/4）实测：** 卷积 187–494 ms、ViT 75–375 ms、音频前填 0.4–0.7 s、文本前填 80–170 ms（其中每轮都会重算 9 个模板头）、生成 200–400 ms。卷积脏段为 110–440 帧，明显大于本轮新增音频的约 100–250 帧，说明全局 Log-Mel 下限变化仍会让部分旧块重算，与 [84](84-android-vad-design.md) 的观察一致。
4. **“把音频前填打到 0.3 秒”这条路径不存在**，因为那是 80–100 个位置的真实计算。剩下能动的只有改变语义的优化（局部 Mel 下限、把模板头/音频/模板尾合并进一个混合批次），收益有限且要重新验证识别质量，按时间盒到此停止。

## 9. 结论与下一步

1. **当前 K90 基线的瓶颈已从「单遍算不过来」变成「串行轮次 + 线程数不足」。** 默认 8 前填 / 6 编码 / 4 生成后，10 秒混说的无更新间隔约 2.4–2.7 s、停录等待约 0.9 s；20 秒输入约 2.8 s / 0.7 s；33 秒连续听写约 4.4 s / 0.05 s（后两项为前填 4 线程时的数据，前填 8 后应更低，未复测）。
2. **默认已采用编码 6、生成 4、前填 8 线程**（`DEFAULT_ENCODE_THREADS` / `DEFAULT_GEN_THREADS` / `DEFAULT_PREFILL_THREADS`）。8 编码线程只再多约 0.15 s 停录等待且占满全部核心，6 留给采集与界面；前填从 4 提到 8 是第 8 节的主要收益。
3. **窗口保留 16 秒。** 8 秒窗没有带来收益，反而在每个回归用例上都比 16 秒窗慢（见第 7 节），因为多一次窗口重置与重复编码；8 秒窗只作为需要压低单轮定稿段长时的备选。
4. **不预览只分段不可作为默认体验**，首字 10.4 s 不可接受；它只适合作为算力不足时的降级档。
5. **剩余问题**：`Q-E08` 的「例三十」「并二次绑定/并二十八d」由 16 s 附近切分与模型本身共同导致，换窗无法规避；下一轮应做「按 VAD 边界或错开整秒切断」的边界实验，而不是继续调线程。音频前填的诊断结论见第 8 节：不是异常开销，无法再靠“修 bug”压缩。
6. 未覆盖：真人麦克风、长时间过热降频、真实 UI 绘制与功耗、日常包体积与首装；本轮结论只来自合成语料实时回放与隔离包前台保活。

## 10. 复跑入口

构建与安装：

```powershell
scripts/gradle.ps1 '-Psayin.instrumentationBuildType=imageTest' :app:assembleImageTest :app:assembleImageTestAndroidTest
adb -s f3ba305a install -r android/app/build/outputs/apk/imageTest/app-imageTest.apk
adb -s f3ba305a install -r android/app/build/outputs/apk/androidTest/imageTest/app-imageTest-androidTest.apk
```

每轮必须让隔离包保持前台，否则 HyperOS 冻结会让用例退化到分钟级。默认值即 16 秒窗 / 编码 6 / 生成 4 / 前填 8 / 节奏门控，下面是最小复跑命令：

```powershell
adb -s f3ba305a shell am start -W -n seeyuer.sayin.imagetest/androidx.activity.ComponentActivity
adb -s f3ba305a shell am instrument -w -r -e class 'seeyuer.sayin.asr.ImportedAsrInstrumentedTest#recognizesMixedSpeechFromModelFolder' `
  -e asrModelId r2t2 -e asrVad true -e asrLong true `
  seeyuer.sayin.imagetest.test/androidx.test.runner.AndroidJUnitRunner
```

要复现本轮的对照配置，在上述命令里追加：`-e r2t2WindowMs 8000 -e r2t2PreviewStepMs 2000 -e r2t2PreviewMode paced -e r2t2EncodeThreads 8 -e r2t2GenThreads 4`。

参数含义：`r2t2PreviewMode` 取 `paced`（节奏门控）、`fixed`（固定 2 s 步长，复现旧调度）、`off`（纯分段）；`r2t2WindowMs` 4000–16000；`asrCorpus Q-A06,Q-E05,Q-E09` 逐条跑 legacy/v3，`asrContinuous true` 用于连续听写；语料放在隔离包 `files/voice-corpus/`，模型放在 `no_backup/local-models/r2t2/`。
