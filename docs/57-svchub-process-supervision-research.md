# 57 · SvcHub 调研：Root 进程监督与 SayIn 的取舍

日期：2026-11-15。状态：**源码调研完成；未安装 SvcHub，未实现或验收 SayIn Root 模块**。

后续进展：用户随后指定 C++，原 Kotlin 守护设想已替换为原生采集父/子进程，限定实施与证据见 [60](60-root-helper-native-clipboard-collection.md)。本文保留调研时的机制分析；应用保活仍未实施，不引入 SvcHub 运行依赖。

## 1. 结论与需求对应

SvcHub 是 Root 环境中的通用服务管理模块，主要监督 Termux 命令和二进制进程。它可以参考，但不是可以直接接入的 SayIn 剪贴板/应用保活方案。

用户需要的是：**SayIn 不运行时仍能采集剪贴板；需要后台待命时，业务进程被系统回收后可以有条件恢复**。两者独立启停。对应关系如下：

| 需求 | SvcHub 已有能力 | 对 SayIn 的判断 |
| --- | --- | --- |
| 开机启动独立采集进程 | 模块入口启动监督器，再启动配置的命令 | 可以借鉴生命周期组织 |
| 独立采集跨应用剪贴板 | 没有剪贴板采集、过滤或历史实现 | 仍需解决平台入口、权限与持久化 |
| 监督自己的长运行进程 | PID 文件、探活、定期重新启动 | 思路可用，但身份校验、实例锁和重启预算需要重新设计 |
| 恢复 Android 业务待命 | 可运行启动命令，没有 App 业务握手 | 不能把命令已执行/PID 存在当作 App 已就绪 |
| 尊重用户强停 | 通用巡检不会判断 Android 停止原因 | 不能直接套用 |
| 保留 SayIn 发送安全边界 | 不认识草稿、Outbox、held、uncertain | 必须由现有 App 业务所有者继续负责 |

建议保持 [56 的单模块方案](56-root-module-clipboard-and-keepalive-design.md)：短启动脚本、独立 Kotlin 守护、最小采集入口、固定操作的鉴权 IPC。**不额外要求用户安装 SvcHub，也不把 SayIn 变成通用 Root 服务管理器。**

## 3. 实际运行机制

```text
Root 管理器的 service.sh
  → 加载配置、清理运行文件、运行可选开机命令
  → 可选启动 BusyBox HTTP/WebUI
  → nohup 启动 supervisor.sh
      → 等待系统启动 / 解锁 / su
      → 检查配置为 auto=start 的服务
      → PID 不存活则 setsid + su 执行命令
      → 分段休眠、重读配置、检查策略，再巡检
```

| 部分 | 源码位置 | 行为 |
| --- | --- | --- |
| 开机入口 | [service.sh](../refer/SvcHub-master/service.sh) | 检查停用标记、初始化、拉起监督器 |
| 监督循环 | [supervisor.sh](../refer/SvcHub-master/supervisor.sh) | PID 探活、自动启动、分片休眠和策略检测 |
| 进程控制 | [lib/proc.sh](../refer/SvcHub-master/lib/proc.sh) | `setsid`、PID 文件、进程组停止 |
| 配置 | [lib/config.sh](../refer/SvcHub-master/lib/config.sh) | 白名单配置键、边界检查、临时文件替换 |
| 运行条件 | [lib/policy.sh](../refer/SvcHub-master/lib/policy.sh) | 时间窗、屏幕/解锁、Wi-Fi、可选内核唤醒锁 |
| 管理入口 | `httpd.sh`、`action.sh`、`webroot/cgi-bin/api.cgi` | HTTP CGI、会话鉴权、服务及命令管理 |
| 更新 | `lib/update.sh`、`updater.sh` | 查询制品、下载、可选摘要校验和替换 |

默认巡检 60 秒，配置限制为 10～86400 秒。长间隔拆成不超过 60 秒的片段，部分屏幕/解锁场景缩短到 10 秒。所谓屏幕/Wi-Fi 变化响应仍以周期检查实现，不能称为系统事件驱动或立即恢复。

它没有展示通过调整 App OOM 优先级、修改 LMKD 等实现“不被杀”的机制。可选内核唤醒锁与重启监督也不能保证进程永远存活。监督器由开机脚本一次性拉起；本地代码不能证明监督器自己退出后一定会被另一个持续运行的父监督者恢复。

## 4. 关键实现不能直接照搬

### 4.1 PID 存在不等于身份正确或业务就绪

`lib/proc.sh:7` 的 `pidfile_alive()` 主要检查 `kill -0`，没有绑定 UID、命令行、进程启动时间和系统启动身份。PID 复用可能导致误判。停止路径会检查 PID 是大于 1 的数字，但仍没有解决进程身份复用。

`start_svc()` 记录自己启动的 `setsid/su` 包装进程 PID；Android App 由 ActivityManager 创建，不是 `am startservice` 命令的 PID。即便启动命令成功返回，也不能证明 App 服务完成初始化，更不能证明电脑连接恢复。巡检启动后等待约 0.3 秒的探活不属于业务握手。

SayIn 应分别确认**模块进程身份、待命服务鉴权握手、电脑连接状态**。不能用启动 App 的 shell 命令 PID 监督 App，也不能将通用进程组强杀用于 Android App。

### 4.2 单实例保护存在静态竞态

`supervisor.sh:8` 先检查 PID 文件，再写入当前 PID，没有原子实例锁。`service.sh:15` 又在检查监督器之前调用 `clean_temp_files()`；`lib/core.sh:232` 会删除运行目录顶层文件，包括 PID 文件。重复调用入口可能清掉仍运行实例的身份记录。

这不是本次真机复现结果。SayIn 仍须从设计上避免：清理前取得原子实例锁，确认旧实例退出；配置更新与启动串行化；不能靠“先查再写”保证唯一历史写入者。

### 4.3 手动停止不等于停止自动恢复

`stop_svc()` 停止进程并清理 PID 等文件，不同时把服务的 `auto=start` 改为关闭，也没有 Android 用户停止锁存状态。自动巡检开启且启动条件满足时，下轮可能再次启动。

另外，关闭周期巡检并不禁止开机首轮启动，部分策略恢复也可放行一次。这是 SvcHub 的通用服务策略，不符合 SayIn 用户主动停止后不被偷偷拉起的要求。

SayIn 必须区分明确的系统回收、用户停止和原因未知；未知不激进恢复。Android 设置强停、前台任务管理器 Stop 及用户明确停止待命均不能靠周期拉起覆盖。App 停止与独立剪贴板采集开关仍是两个维度。

### 4.4 固定巡检没有逐服务崩溃预算

当前循环未见每服务的连续失败计数、指数退避或熔断。持续崩溃的命令可在每轮巡检重新执行。SayIn 需保留 56 的有界恢复预算、冷却和失败可见性；断网、电脑离线不能当成进程故障而重启 App。

### 4.5 解锁检测偏向可用性，不能当隐私边界

启动等待最多约 300 秒，超时后继续巡检。CE 属性为空也可放行；`keyguard_locked()` 无匹配返回未锁，屏幕状态未知回退为亮屏。这些兜底适合它的服务启停取舍，不能证明用户已经解锁。

SayIn 涉及剪贴板和私有加密数据，用户解锁/可访问性无法确认时应暂停相关操作并报告原因，不能把探测失败解释成允许采集或解密。

### 4.6 配置替换不等于完整事务

白名单解析、值校验、权限和临时文件替换值得借鉴；但固定 `.tmp` 名称、缺少统一写锁和落盘同步，不能提供多个写入者之间的事务保证。SayIn 历史和配置由唯一守护所有者写入，清空屏障、加密与崩溃一致性另行验收。

## 5. 管理、安全与不需要继承的部分

SvcHub 的 WebUI 默认绑定 `127.0.0.1:5555`，有密码/会话/Token、默认密码更改限制及部分请求防护；不能描述为默认向整个局域网开放的无鉴权 Root 接口。

但其授权主体是持有管理凭据者，没有 SayIn 需要的 App UID/签名绑定。`api_run_cmd()`、开机命令和二进制服务配置本来就允许执行命令；少数危险命令的正则拦截是防误操作，不能充当命令沙箱。

SayIn 不需要继承通用命令编辑器、Termux 环境、Root HTTP 服务、任意服务清单、SSID/亮屏/定时策略或全局 DNS 覆盖。管理入口复用 SayIn 设置页；本地 IPC 只允许固定的历史管理/状态/启停/握手操作，不提供 `runShell(command)`。

更新代码在缺少预期 SHA-256 时允许跳过完整性校验；即便有摘要，也不能据此声称拥有独立可信的签名更新链。SayIn 不直接沿用其 Root 二进制自动下载/替换能力，也不从代理元数据静默更新高权限代码。

许可证尚未确认，当前只借鉴机制，不拷贝脚本或引入代码依赖。

## 6. 对现有方案的实际影响

不改变 [56](56-root-module-clipboard-and-keepalive-design.md) 的职责边界，仅补强实施依据：

1. **监督模块自己的进程**：采用固定产物和固定参数，原子实例锁、代次及真实身份校验；脚本短小，不做通用服务平台。
2. **监督 App 的待命能力**：使用固定组件及鉴权握手，App 继续持有唯一业务所有者；当前不因“进程保活”新建第二个 `:runtime` 业务所有者。
3. **启动与停止均可确认**：仅恢复可确认的异常，预算用尽停止尝试；停用/更新须等待旧实例实际退出，不能只删除 PID 文件。
4. **停止不授权发送**：恢复不打开 Activity、不录音、不加载无需求模型；旧请求先查询，不重放、不释放旧 held、不清除 uncertain、不复活自动发送票据。
5. **状态与权限分开**：Root 监督无法代替剪贴板读取权限、平台采集入口、后台服务启动条件或厂商自启动设置。悬浮球/前台通知沿用现有生命周期，不重复叠加服务；自启动说明保留非阻断引导。

下一步仍是 56 的 A 阶段原型：目标 ROM 上证明独立采集、可信 IPC、后台待命恢复及用户停止语义。不能因为 SvcHub 能启动 shell 服务，就跳过这些门槛进入完整模块开发。
