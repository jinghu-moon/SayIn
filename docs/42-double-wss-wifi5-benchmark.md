# 42 · 双 WSS 与双 TLS 同期真机对照

日期：2026-11-14。状态：独立网络原型补测完成，未修改生产通信协议或图片业务。

后续：[43 Kotlin / OkHttp 图片通道对照](43-kotlin-okhttp-image-upload-benchmark.md)已实测项目运行时的双 WSS 与 WSS＋HTTPS，并加入限速、内存采样及取消探针。本文件客户端为 Rust，以下结果保持原实验范围，不直接与 Kotlin 结果计算提升。

## 1. 结论

**双 WSS 可以保留接近双 TLS 的图片吞吐，并明显改善单 WSS 的控制排队；本次控制尾延迟仍是双 TLS 更低，不能将两者称为完全等价。**

使用同一手机、电脑及八张原始 JPEG，单 WSS、双 WSS、双 TLS 交错运行六轮，共 **144 次上传、1,813,819,518 字节图片、11469 个控制 echo RTT 样本**。所有上传均通过完整长度和 SHA-256 校验，连接错误、上传超时及服务端错误日志均为零。

| 同期指标 | 单 WSS | 双 WSS | 双 TLS，raw 二进制帧 |
| --- | ---: | ---: | ---: |
| 10.08MiB 传输中位耗时 | 1.020 秒 | 1.058 秒 | 1.108 秒 |
| 25.17MiB 传输中位耗时 | 2.504 秒 | 2.554 秒 | 2.666 秒 |
| 55.94MiB 传输中位耗时 | 5.997 秒 | 5.717 秒 | 5.966 秒 |
| 大图期间控制 RTT p50 | 1050.0ms | 63.3ms | 26.6ms |
| 大图期间控制 RTT p95 | 1673.0ms | 140.5ms | 83.5ms |
| 大图期间控制 RTT p99 | 1944.3ms | 188.5ms | 143.3ms |

双 WSS 的三种大图中位耗时比同期双 TLS 低 4.2%～4.5%，没有观察到需要为了图片吞吐引入 raw TLS 帧的优势。控制 p95 则比双 TLS 高约 **57ms**；相对于单 WSS，双 WSS 的控制 p95 降低约 **91.6%**。

对 SayIn 的含义：双 WSS 已具备作为首版简化方案的实测依据，可以复用现有 WebSocket 库、连接管理及二进制消息能力；但这是以减少额外传输实现为理由的候选，**不能声称它取得了本次最好的满载控制延迟**。如果后续确定了更严格的延迟目标，应保留双 TLS 对照，并继续测试缓冲和发送节奏。当前没有经用户确认的控制延迟 SLO，本次不替用户设定可接受上限，也不直接替换生产协议。

## 2. 公平对照与环境

本次重新运行单 WSS 和双 TLS，不直接拿第一次实验的三轮数字作同期比较。旧实验保留于 [41 实测记录](41-image-transport-wifi5-benchmark.md)，本报告表格全部来自这次六轮数据。

| 项目 | 实际条件 |
| --- | --- |
| 代码基线 | `f9b52bec3513515d14be3ebd75fac1946120e7b3` + 首次实验未提交工具；在原隔离 worktree 继续扩展 |
| 手机 | Redmi K40 / M2012K11AC，Android 13 / API 33 |
| Wi-Fi | Wi-Fi 5，5825MHz，Tx/Rx 协商速率 192Mbps |
| RSSI | 开始、结束均约 -52dBm |
| 电脑 | 同局域网千兆以太网，精确绑定 `192.168.71.6` |
| 手机绑定 | `192.168.71.72`，TCP 测试端口 `62190` |
| TLS/运行时 | TLS 1.3 + rustls/ring；Rust 1.99.1 release；双端各四个 Tokio worker |
| 应用预算 | 图片正文 48KiB/块，图片队列两块/连接；控制队列 32 项，优先于尚未写出的图片块 |
| TCP | TCP_NODELAY 开启，系统默认缓冲/拥塞控制，无人工限速 |

三种模式唯一主要变化是连接数及其应用帧承载方式：

- 单 WSS：控制和图片共享一个 WebSocket/TLS/TCP 连接。
- 双 WSS：两个独立 WebSocket/TLS/TCP 连接；控制连接承载开始/确认、echo 和最终摘要确认；图片连接承载相同的二进制块及结束标记。不使用 Base64，不增加图片并行。
- 双 TLS：两个独立 TLS/TCP 连接，分工与双 WSS 相同，承载原实验的四字节长度头 + 二进制记录。

两条 WSS 均验证本次临时证书、TLS 名称及完整 DER，在验证后使用同一临时 token 和 session 关联。测试用的关联协议不是产品配对实现，不证明生产设备撤销、会话轮换等已接入。客户端图片路由在两条连接模式使用第 2 条连接；服务端图像连接不能提交控制 ping/start，最终完成确认通过第 1 条连接返回。

样本按实际字节和摘要识别，与上轮相同，未修改原图。发送方有界读取，接收方流式计算 SHA-256 后丢弃；未解码或存储图片。耗时仍从上传开始请求到接收摘要确认，连接准备另计。控制 echo 约 20ms 一次，使用同一手机单调时钟；各模式前/后分别采集 1.5/1 秒空闲 RTT。

## 5. 控制延迟及轮间差异

以下负载百分位仅包含三张 ≥10MiB 图片期间发出的控制 echo；样本在每轮中相关，不能当作数千个独立网络环境。百分位采用 nearest-rank，数值是往返时间，包含应用排队及调度。

| 配置 | 空闲样本数 | 空闲 p50 | 空闲 p95 | 大图样本数 | 大图 p50 | 大图 p95 | 大图 p99 | 大图最大 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 单 WSS | 749 | 2.5ms | 11.1ms | 2863 | 1050.0ms | 1673.0ms | 1944.3ms | 2204.0ms |
| 双 WSS | 753 | 2.5ms | 19.1ms | 2841 | 63.3ms | 140.5ms | 188.5ms | 286.7ms |
| 双 TLS | 754 | 2.4ms | 18.0ms | 2941 | 26.6ms | 83.5ms | 143.3ms | 205.6ms |

每轮的大图控制 RTT p95（毫秒）：

| 轮次 | 单 WSS | 双 WSS | 双 TLS |
| --- | ---: | ---: | ---: |
| 1 | 1419.0 | 89.6 | 45.5 |
| 2 | 1861.7 | 158.7 | 95.3 |
| 3 | 1853.0 | 101.6 | 86.7 |
| 4 | 1457.0 | 85.9 | 88.7 |
| 5 | 1667.0 | 164.0 | 68.6 |
| 6 | 1598.9 | 139.1 | 88.1 |

双 WSS 每轮均显著优于单 WSS；双 TLS 在六轮中的五轮低于双 WSS，第四轮两者接近且双 WSS 略低。空闲 RTT 中位数均约 2.5ms，不能用空闲延迟代替满速传图时的控制响应。

本次不能把双 WSS 多出的控制延迟全部归因于 WebSocket 帧头或掩码：没有单独控制内核排队、发送节奏、无线调度或剖析其 CPU/锁开销。保留实测差异，不编造单一根因，也不将相关性当成协议固有定律。
