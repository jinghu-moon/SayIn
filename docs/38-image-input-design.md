# 38 · SayIn 手机发送图片与电脑输入设计

日期：2026-11-14；实施启动：2026-11-15。状态：**用户已选定双 WSS，按阶段实施中**。独立网络原型已完成 [Wi-Fi 5 真机实验](41-image-transport-wifi5-benchmark.md)；本地图片输入原型及后续生产实施进度见 [45 实施记录](45-image-input-implementation.md)。尚不能把独立原型描述为生产图片功能。

最终承载决定：保留现有控制 WSS，增加按需打开的图片 WSS；两者使用同一精确绑定的监听端点、TLS 1.3 和已配对完整固定证书。图片走有界二进制顺序块，不走 Base64，不增加单图并行、raw TLS 或 QUIC 生产依赖。选择依据是既有栈复用、控制与大载荷隔离及实测足够合理的性能，不是所有指标最优。不写死 60Mbps 带宽限制。以下实验段落保留各轮当时的判断，以上述最终决定为准。

补测更新：[42 双 WSS 与双 TLS 同期六轮对照](42-double-wss-wifi5-benchmark.md)已完成 144 次真实局域网上传。双 WSS 与双 TLS 大图吞吐接近，控制 RTT p95 分别约 141/84ms，均明显优于单 WSS 的 1673ms。双 WSS 可作为复用现有 WebSocket 的简化候选，但不能描述为与双 TLS 控制尾延迟完全相当；生产承载尚未替换，具体结果与限制以该记录为准。

Kotlin 客户端补测：[43 Kotlin / OkHttp 真机对照](43-kotlin-okhttp-image-upload-benchmark.md)使用项目 Kotlin 2.4.21 / OkHttp 5.5.1，完成双 WSS 与 WSS＋HTTPS、各自不限速/60Mbps 四配置共 128 次上传及 16 次取消。两种承载控制 p95 约 90/89ms，没有稳定的 HTTPS 优势；限速后约 40/42ms，但最大图耗时增加。当前优先验证双 WSS 与有界发送节奏，不写死产品带宽，也不因协议名称增加承载；前两份 Rust CLI 数字不得与 Kotlin 数据混作同期比较。仍未替换生产协议或验收图片上屏。

完整补测：[44 Kotlin 全传输同期对照](44-kotlin-all-transports-wifi5-benchmark.md)已覆盖双 WSS、WSS＋HTTPS、双 TLS、QUIC 1/2/4 图片流及各自总60Mbps 档，384 次上传、48 次取消全部通过。本轮最大图 HTTPS 最快，前两张大图双 TLS 最快，不限速控制 p95 则双 WSS 最低；QUIC 并行没有线性提速，固定限速也未稳定改善 WSS/HTTPS p95。没有方案全面领先；双 WSS 仍是复用成本较低的候选，不能称性能全部最优。43 的限速收益只属于当次环境，不作为通用保证；具体库差异及全部实测范围以 44 为准。

## 1. 目标与范围

手机选择一张图片并明确发送，电脑通过已有配对信任接收、保存，再向当前前台目标提交一次图片粘贴。支持粘贴图片的聊天框通常进入待发送区，文档编辑区通常插入图片；目标应用的实际行为必须逐项验证，不承诺任意输入框都能显示图片。

首版建议支持单张静态 JPEG/PNG、系统选图、发送前预览、传输进度、接收回执，以及电脑历史中的查看、复制图片、另存为。拍照入口和系统“分享至 SayIn”在核心链路可靠后接入，仍需预览和明确发送。多图、动图、文件通用传输、跨网公网中转、OCR 及向联系人自动发送不在首版范围。

用户确认的是增加手机发图的需求；下文的格式、配额、协议结构和实施顺序是建议设计，须经原型与验收后定案。

## 2. 当前实现与根因

| 模块 | 当前事实 | 需要改变的设计 |
| --- | --- | --- |

## 3. 用户交互

1. 在说话页的辅助入口选择图片，不新建常驻“传文件”主流程。
2. 使用系统选图；显示实际将传送的方向、裁剪结果、透明度及必要缩放说明。取消后保留原有文字草稿。
3. 电脑可接收时点“发送图片”；按钮提交当前图片快照，传输期间不重复创建请求。
4. 电脑完整持久接收后显示“电脑已收到”。满足输入条件时最多自动尝试一次粘贴，不追加 Enter、不抢焦点。
5. 回执显示“已提交粘贴指令”或实际阻断/待核对原因。用户在目标应用确认图片是否出现，是否发给联系人由目标应用及用户决定。

断线、暂停及权限不足时显示直接原因并保留图片。离线允许先选图，但不生成等待未来自动执行的粘贴授权。重连不直接补贴图片，先恢复原请求状态。

首次使用说明自动粘贴会替换系统剪贴板；只需一次清晰说明，不增加每张图片的重复确认。未支持图片的目标无法总被可靠探测，历史始终提供复制与另存为入口，不伪造自动判断成功。

## 4. 图片准备与资源边界

### 4.1 手机准备

- 从系统授权的 `content://` URI 有界读取，不依赖外部原路径长期可用；接收分享时只接受明确支持的内容源及 MIME，不能抓取任意远程 URL。
- 读取头部与实际格式，检查尺寸、像素数、文件长度、动画标记与解码失败；不能仅信任扩展名或外部 MIME。
- 应用方向信息，预览与最终载荷一致；默认清除 GPS 等不必要 EXIF 元数据。JPEG 重编码、缩小或转 PNG 后重新计限，不能把明显降质隐藏成原图传送。
- PNG 保留透明度；拒绝伪装格式、畸形文件和解码炸弹。首版拒绝动画及不支持格式，不默默只取第一帧。
- 形成稳定载荷后计算 SHA-256；重复提交与重试使用已冻结的同一份字节，不重新从 URI 读取另一张内容。

### 4.2 初始预算建议

以下是待验证的拒绝上限，不是性能实测，也不是用户已确认的最终指标。实施前以真实照片、截图及内存测量调整并同步双端协议。

| 项目 | 建议初值 | 依据与限制 |
| --- | --- | --- |
| 单张编码后数据 | 10 MiB | 有界传输、持久化与失败恢复 |
| 解码像素 | 1600 万像素；单边不超过 8192 | 仅 RGBA 就约 64MB，不能只按文件大小估内存 |
| 单块图片正文 | 不超过 48 KiB | 给现有 64 KiB 帧限制及固定头留余量 |
| 上传并发 | 每设备 1 个，主机总计最多 2 个 | 防止多设备占满资源；只有活动发送设备可提交输入 |
| 未引用上传占用 | 主机最多 32 MiB；单次空闲 60 秒回收，绝对期限 5 分钟 | 独立于已接受历史；触顶显式拒绝，不挤掉已有收据 |

Android/Windows 都在分配大块内存前检查，乘法使用溢出保护。展示缩略图在后台按尺寸解码；不能在 GPUI 或 Compose 主线程解码原图。

## 5. 传输协议目标

### 5.1 分开资源传输与外部输入

固定证书、TLS 名称、host/device 认证和连接代次是信任约束，不为图片开放未认证文件服务器。基于四轮实验及用户决定，正式实施采用“一条控制 WSS + 一条按需图片 WSS”，不增加单图并行。控制路径 `/v2` 保持现有 JSON 和消息上限；图片路径 `/v2/images` 复用同一证书、端口、网卡及网络范围，不另开全网卡监听、不增加发现服务或防火墙操作。下面是实施语义，具体消息和代码落地状态以[协议权威文档](01-voicelink-protocol-v2.md)及 45 为准；实现前不能假设现有服务已接受这些消息。

| 阶段 | 拟议语义 | 可发生的副作用 |
| --- | --- | --- |
| begin | 申请上传 ID，声明固定长度、格式、尺寸及摘要 | 预留有限临时资源，不授权粘贴 |
| chunk | 二进制头标识上传 ID、偏移、长度，追加有界块 | 只更新有界临时内存，不产生明文临时文件 |
| finish | 校验总长、摘要、真实格式和解码限制，生成已准备资源引用 | 资源可用于后续提交，不产生系统输入 |
| submit image | 使用请求 UUID、当前 session/target 与不可变资源引用 | 持久接受后进入既有串行输入队列 |
| query/cancel | 查询原请求、取消尚未执行操作或废弃上传 | 不重放输入；取消与执行竞争按实际持久状态报告 |

客户端一次“发送图片”可以自动完成上传与提交，但提交前必须重新核对当前接收范围。上传期间断线、暂停、取消或范围变化使本次粘贴授权失效；完成上传不等于允许以后向新光标提交。

首版不做自动断点续传。重连先查询外部输入请求；明确尚未接受后，用户可重新授权传输。上传传输 ID 与输入请求 UUID 是不同事实，不混用为“恰好一次上屏”的保证。

### 5.2 严格校验与调度

- 上传与设备授权绑定，资源引用不可跨设备猜测使用；session 失效后旧块不得写入新上传。
- 顺序块检查偏移、长度和总量；不支持的重复块/乱序块明确拒绝，不能忽略错误继续产生损坏图片。首版重传需要重新 begin。
- 摘要验证字节完整性，不能代替身份认证。去重指纹继续采用带域分离 HMAC，覆盖图片操作类型、规范元数据、最终字节摘要及目标语义；同请求 ID 换图片必须拒绝。
- 控制与图片大载荷隔离，并分别设置有界写调度；不能仅靠在同一 TCP 字节流中优先插入下一条控制消息。[实测](41-image-transport-wifi5-benchmark.md)中，即使已有 48KiB 分块及控制优先，单 WSS 大图期控制 RTT p95 仍约 1.57 秒。分离 TLS 改善至约 77ms，但仍需测量慢网、取消、暂停和缓冲/发送节奏，不能承诺已经进入网络的数据可被抢占。
- 对 begin/chunk/finish 增加速率与总配额；字节计数通过索引/事务维护，不每次扫描全部历史。未知能力明确拒绝，不降级成文字路径或 Base64 文本。

## 6. 持久化与崩溃恢复

### 6.1 手机

Outbox 继续以 host/device 双重范围隔离，扩展为类型化载荷。图片持久文件使用 Android Keystore 派生保护方案及私有目录，包含必要认证信息；不得把大图整块塞进现有小载荷字段或保存临时 URI 充当已持久载荷。

文件先完整写入并校验、原子提交，再由 Room 事务记录不可变引用及待发送请求。启动修复能够识别孤儿临时文件，引用资源缺失/解密失败停止发送，不能重建身份或替换图片来满足旧请求。清理只回收确认无引用的临时资源，未终结请求保留恢复材料。

### 6.2 Windows

账本协调线程继续独占 SQLite；后台资源 I/O/解码由有界工作任务完成，协调线程只接收结果及事务命令。阶段 2 对 10MiB 上限采用当前用户 DPAPI 直接保护完整资源信封，无需额外文件密钥体系；信封绑定 host/device/resource/不可变元数据，检测同用户下的文件替换。Android 复用已存在的 Keystore AES-GCM，使用独立图片 AAD 域。两端都不把原图或缩略图明文暂存磁盘。上传顺序块先保存在有限、可取消的内存中，finish 后验证并加密落盘；完整 App 峰值内存仍须在阶段 6 测量，不把 decoder 的 best-effort allocation limit 当成进程内存硬限制。

先把受保护资源完整落盘并同步，再以 WAL/FULL 事务绑定资源、接受顺序、配额、历史及收据，提交后才回“电脑已收到”。文件系统与 SQLite 不属于同一个原子事务：必须明确中断点、孤儿回收及引用缺失的失败恢复，不能声称跨两者原子提交。

执行标记须在任何剪贴板写入或按键提交前持久化；终态提交后才发布持久回执。执行中崩溃按 `uncertain` 恢复，待执行按既有 `held` 恢复。接收后的 30 秒期限从接受图片操作算起，上传阶段有独立期限；人工 release 不续期，不因资源已收到自动粘贴。

正文资源的展示保留策略与现有历史一致，默认保留；删除/保留期只清理展示载荷及缩略图，不删除收据、请求指纹和去重身份。已接受的资源不能因上传临时配额而被驱逐；磁盘不足停止新接受并解释原因。

## 7. Windows 图片粘贴执行

### 7.1 格式

首个兼容原型提供 `CF_DIBV5` 及注册的 PNG 格式，具体格式顺序、透明度和颜色行为通过应用矩阵验证。必要时评估 `CF_DIB` 回退；同一剪贴板可提供同内容的多个表示，但目标选择哪种格式由目标应用决定。

首版不自动提供 `CF_HDROP`、文件路径文本或 HTML：图片与文件附件具有不同语义和临时文件寿命要求。若以后增加“作为文件发送”，应作为明确操作设计，不能在图片粘贴失败后偷偷改成文件或路径。

### 7.2 执行步骤

1. 后台完成受保护资源读取、解码、格式构造与上限检查；长时间准备在捕获最终目标之前完成。
2. 串行输入线程沿用 `NativeInput` 的前台窗口、进程创建时间、会话、输入桌面、完整性级别及修饰键核对；不是窗口标题匹配。
3. 执行时目标 metadata 先持久化，提交执行标记，随后重新核对暂停代次及目标租约。
4. 有界尝试打开剪贴板并一次发布所有已准备格式；正确处理 Win32 内存所有权与部分格式发布失败。剪贴板仍忙则停止，不固定睡眠无限重试。
5. 关闭剪贴板后核对内容序列/归属、闸门与目标，再通过一次 `SendInput` 批量提交 Ctrl/V 的按下与释放；不抢焦点，不追加 Enter。
6. 检查返回事件数和事后目标；部分提交、途中失焦或无法确认结果进入 `uncertain`。必要的修饰键释放必须只处理本操作按下的键，不重复发出粘贴快捷键。
7. 协调线程持久终态并通知 UI/手机；粘贴事件入队不等于目标已读取图片。

用户修改剪贴板或切换焦点时，核对只能缩小竞态窗口，无法原子锁定 Windows 剪贴板、前台窗口与目标应用读取。没有提交按键时可以报告粘贴未尝试；有可能发生输入时保守报告待核对。

### 7.3 剪贴板生命周期

自动粘贴会替换原内容。首版不承诺完整恢复任意私有/延迟渲染剪贴板格式，也不在固定延迟后恢复旧内容；目标可能尚未读取，用户也可能已复制新内容。默认留下本次图片，不启动后台反复覆盖或定时清空。

设置 Windows 的剪贴板历史/云同步排除标记，降低系统历史及跨设备同步收录；不能声称这些标记阻止第三方剪贴板工具或本地进程读取。复制图片操作同样遵守此策略。剪贴板写入后再失败时，提示中不能隐瞒图片已经进入系统剪贴板。

## 8. 回执、历史与手动恢复

| 状态事实 | 建议文案语义 | 禁止误报 |
| --- | --- | --- |
| 上传中/已准备资源 | 传输中/图片已准备 | 不称电脑已接受输入 |
| 收据事务已提交 | 电脑已收到，等待粘贴 | 不称已显示或已发送给联系人 |
| 全部粘贴事件已提交 | 已提交粘贴指令，请查看目标应用 | 不称已确认上屏 |
| 确定未提交按键 | 未粘贴，并给实际原因；若写过剪贴板则说明 | 不自动换新请求重试 |
| 可能已输入/执行中崩溃 | 结果待核对 | 不自动补贴，不由手机远程解除本地核对 |

历史保存缩略图、来源设备名称快照、接受时间、实际执行目标与结果。目标归属来自执行时持久记录，不在浏览时抓当前窗口补填。未执行的图片不虚构目标程序。

“复制图片”只写剪贴板，不顺带模拟粘贴；“另存为”通过用户选择路径导出；“重新粘贴”属于用户明确的新操作，重新获取当前目标与授权。`unknown`/`uncertain` 的原请求必须先按既有规则查询或核对，不能用历史按钮绕过去重。

## 9. 实施阶段与验收

用户要求每个阶段通过该阶段全部测试后独立提交并推送，再进入下一阶段，直到完成全部任务。阶段状态、提交及未验证项逐项记录在 45，禁止把局部原型或 fake adapter 覆盖记成整链路验收。

1. 建立现有文字/按键/暂停/Outbox 基线，选定真实目标应用清单。
2. 在独立原型验证本地 PNG/JPEG 的剪贴板格式、透明度与一次粘贴，先确认输入能力边界。
3. 实现类型化操作、分块传输、双端受保护资源、事务配额及故障恢复；再接 UI 与历史。
4. 执行自动回归、故障注入和真实 Wi-Fi/应用验收；最后评估拍照与系统分享入口。

| 验收维度 | 必测内容 |
| --- | --- |
| 图片 | 横竖 EXIF、透明 PNG、中英截图、大小边界、畸形/伪装/超大尺寸、解码炸弹 |
| 传输 | 慢网、取消、断线、重复块、错误偏移、摘要不符、超额、多设备、控制优先与范围变化 |
| 持久化 | 文件写入、引用事务、接受提交、执行标记、剪贴板写入、按键提交和终态提交之间逐点崩溃 |
| 去重 | 同请求同图不重贴、同 ID 换图拒绝、先查询再人工恢复、重启和重连不重放 |
| 原生输入 | 普通/高完整性目标、目标切换、用户复制新内容、剪贴板忙、修饰键按住、锁屏与暂停 |
| 真实应用 | 用户常用聊天软件、Word/WPS 或文档编辑器、浏览器上传区、纯文本编辑器；记录精确版本和结果 |
| 回归 | 原有单行文字、Enter、队列期限、历史删除/恢复、托盘、配对撤销和 i18n |

真实应用矩阵要记录是否显示、透明度、是否产生附件、是否误发消息、是否改变目标；粘贴到纯文本框时不得自动打开程序或发送正文。仅 fake adapter 通过不足以验收图片输入。

后续代码变更执行项目规定的 Android JVM/构建/Lint/i18n、完整桌面测试/Clippy/包限定格式/构建/依赖检查，并用隔离命名空间运行双端回归。记录端到端传输与执行 p50/p95/p99、峰值内存及暂停响应，限额与并发优化以数据为依据。
